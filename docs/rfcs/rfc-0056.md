# RFC-0056: Persistence — delegate to the host serializer; framec owns only the frame

- **Status:** Draft
- **Author:** Mark Truluck <mark.truluck@cogiton.com>
- **Created:** 2026-07-15
- **Supersedes:** [RFC-0053](rfc-0053.md), [RFC-0054](rfc-0054.md), [RFC-0055](rfc-0055.md)

The key words **MUST**, **MUST NOT**, **SHOULD**, **SHOULD NOT**, and **MAY** are to be
interpreted as in RFC 2119.

## Summary

Frame persistence saves a `@@[persist]` system and restores it into a **fresh instance of the
same program, in the same language**, indistinguishably. framec does **not** implement
serialization. It delegates the marshalling of every value to that language's **own best
serializer**, and confines its own generated code to the things a serializer cannot know: which
fields persist, the machine's live **control state**, restoring **without running the
constructor**, and — only in languages whose runtime cannot otherwise recover a value's type —
supplying **type identity** safely. Cross-language portability and any framec-owned wire format
are **out of scope**.

## Motivation

Persistence has been re-litigated repeatedly, and the cause is a single conflation. Earlier
designs aimed at a **uniform, framec-owned persistence format** spanning every target. That goal
silently demands three things that cannot all be true at once:

1. **type-ignorance** — framec writes no per-type serialization code;
2. **faithful user types** — a user-defined type, nesting, and collections all round-trip;
3. **no dependency** — framec borrows nothing from the target's ecosystem.

You can have any two. The attempt to have all three produced a hand-rolled "flat format" that
handled only scalars and, to do even that, branched on the field's type — violating (1) — while
a genuinely good, framec-owned envelope carried Python. The result was an **inconsistent hybrid
nobody could reason about**: one target served by a real mechanism, others by a scalar stopgap
wearing the same name.

The way out is to name the actual goal and drop the false one:

- The goal is **single-language round-trip**. That is achievable today.
- A **portable, cross-target, framec-owned format** is a different and far larger ambition. It
  is not required for single-language round-trip, and pursuing it is what kept resurrecting
  "should we build our own serializer?"

And the answer to that question is **no**. For a single language, the best serializer is that
language's own library — serde, `Codable`, `encoding/json`, `System.Text.Json`, Jackson. framec
will not equal or beat them and should not try. framec's value is not a serializer; it is
knowing the **Frame-specific** things a serializer does not.

## The contract

### Scope

- A snapshot produced by a program **MUST** restore into a **fresh instance of the same system,
  compiled from the same source, in the same language**, reproducing all observable state.
- Cross-language restore — a snapshot from target *X* revived in target *Y* — is **out of
  scope**. framec defines **no** portable wire format, and no target's snapshot bytes are a
  contract another target must read.

### The delegation principle

- framec **MUST NOT** implement value serialization. For every persisted value, the target
  language's **standard serializer** performs the marshalling of that value.
- framec's emitted persistence code **MUST** be **type-ignorant**: it emits the user's declared
  field types verbatim, plus whatever derive/attribute the serializer requires (e.g. Rust's
  `#[derive(Serialize, Deserialize)]`), and contains **no branch on a user type name**.
- **The rule:** *framec builds its own persistence mechanism only to supply a capability the
  host language lacks. It **MUST NOT** re-implement a serializer the host already provides.*

### What framec owns — on every target

A serializer knows how to turn a value into bytes. It does not know these, so framec **MUST**:

- **Manifest** — persist exactly the `domain:` fields that are not marked `@@[no_persist]`.
- **Control state** — the live machine state (the current state, and the stack for a
  state-stack machine) **MUST** round-trip. No general-purpose serializer models this.
- **Construction bypass** — restore **MUST** populate a fresh instance **without** running the
  user's `$>`/constructor (consistent with factory-only construction), so restoring cannot
  re-fire lifecycle side effects.
- **Schema check** — a snapshot whose schema does not match the running program **MUST** be
  refused with a diagnostic, never silently mis-restored into a different shape.

These four, plus the type-identity work below, are the **entirety** of framec's own persistence
code. Everything else is the serializer's job.

### The two regimes — determined by the language, not by choice

Whether framec must supply type identity is a property of the target language, not a design
preference. This yields two regimes, and every statically- or dynamically-typed target falls
into one. (A third, below, is for dynamic languages that cannot reflect at all.)

- **Regime A — statically typed** (Rust, Go, Swift, C#, Kotlin, Java, Dart, C++, C). framec
  knows each field's type at generation time and hands it to the serializer, which deserializes
  **into that declared type**. The bytes are **pure data with no type tag**. A user value that
  happens to contain a marker-like key is inert — it is deserialized as whatever the declared
  type says. Type-mimicry restoration (the failure a prior design shipped, where a user
  container carrying a reserved type key was rebuilt as a typed instance) is therefore
  **impossible by construction** on this regime, and framec adds no framing to prevent it
  because none is needed.

- **Regime B — dynamically typed and reflective** (Python, JavaScript/TypeScript, Ruby, PHP).
  framec has no compile-time type, and the target's plain serializer (e.g. `json`) will not, on
  its own, reconstruct a user-defined class. framec **MUST** therefore place the value's type
  identity **in the snapshot**, and it **MUST** do so **out of band** — in an envelope whose
  slots cannot collide with the user's own data — so a user container that merely contains the
  envelope's key names is never mistaken for a typed value. On this regime framec's own
  mechanism is real and required: the out-of-band envelope, save-time escaping of user data,
  and an **emitted closed-world registry** of the types the program defines.

- **Regime C — dynamically typed and non-reflective** (Lua, GDScript). The runtime cannot name
  a value's type on save or resolve a name on restore. A value that needs a reconstructed
  *type* is beyond what the language expresses; the faithful form is the native container, and
  needing more is a **reachability limit that MUST be reported**, never a silent erasure.

### The closed-world safety floor — Regime B only

On Regime B, restore reads a type name from the snapshot. It **MUST** resolve that name **only
against types the program itself defines**, never against ambient globals, imports, or the
standard library. Visibility is not enough: a type merely reachable in the module namespace but
defined elsewhere (an import, a monkeypatched class) **MUST NOT** resolve. framec emits the
closed-world set as an explicit registry rather than discovering it by enumerating a module or
file. This floor is **non-deferrable** and ships with the reflective route.

### The out-of-band framing requirement — Regime B only

The out-of-band envelope is required **only where framec injects a type tag** — that is, only on
Regime B. On Regime A there is no tag in the bytes, so there is nothing to collide with and the
requirement is moot. A design that mandates the envelope universally is over-generalized; this
RFC scopes it to the regime that has the problem.

### The serializer, per target

R2-style delegation names a concrete serializer for each target. Where the language provides one
in its standard library the choice is forced; where it does not, framec **MUST** pick one and
state it, so persistence has a single, documented mechanism per target rather than a bespoke one.

| Target | Regime | Serializer framec delegates to |
|---|---|---|
| Rust | A | `serde` + `serde_json` |
| Go | A | `encoding/json` (standard library) |
| Swift | A | `Codable` (standard library) |
| C# | A | `System.Text.Json` (standard library) |
| Dart | A | `dart:convert` (standard library) |
| Kotlin | A | `kotlinx.serialization` |
| Java | A | Jackson (or Gson) — a chosen dependency |
| C++ | A | a chosen JSON library (e.g. nlohmann/json) |
| **C** | A | **no standard serializer exists** — see below |
| Python | B | `json` + framec envelope + registry |
| JavaScript / TypeScript | B | `JSON` + framec envelope + registry |
| Ruby | B | `json` + framec envelope + registry |
| PHP | B | `json` + framec envelope + registry |
| Lua | C | native tables; a needed *type* is a reachability limit |
| GDScript | C | Godot resource machinery |

**C is the one genuine exception.** C has no standard serializer and no de-facto one framec can
assume. C persistence is therefore either **limited to scalar and framec-composable shapes**, or
served by a **single framec-emitted encoder** — the one place the delegation principle's "use the
host library" has no host library to use, and thus the one legitimate case for framec's own
value-marshalling code. Which of the two is chosen for C is left to the C persistence work; both
are consistent with this RFC because both are the *minimum* framec must build where the host
supplies nothing.

## Examples

A persistent system delegates entirely; the author writes ordinary Frame:

```frame
@@[persist]
@@system Counter {
    interface:
        bump()
    machine:
        $Counting {
            bump() { @@:self.n = @@:self.n + 1 }
        }
    domain:
        n: int = 0
}
```

On a Regime A target, framec generates a `snapshot()` and a `restore()` that carry the schema and
control state and hand `n` — and any user-typed, nested, or collection field — straight to the
serializer. The author's obligation is only that a user-defined type used in a persisted field is
itself serializable by that language's serializer (in Rust, that it derives `Serialize` /
`Deserialize`): the **self-marshalling requirement**, which the serializer, not framec, enforces.

```frame
// A user type in a persisted field — round-trips because the serializer handles it,
// not because framec wrote any code about `Vec2`.
@@[persist]
@@system Body {
    interface:
        step()
    machine:
        $Moving {
            step() { @@:self.pos = @@:self.pos }
        }
    domain:
        pos: Vec2 = Vec2::default()
}
```

On a Regime B target the same source produces a `snapshot`/`restore` pair that additionally wraps
each typed value in the out-of-band envelope and resolves types on restore only against the
program's own closed-world registry.

## Alternatives

- **A uniform, framec-owned format across every target.** Rejected. That is *cross-language
  portability*, a separate and much larger project than single-language round-trip, and it forces
  framec to re-implement — across seventeen targets — serialization the languages already do
  better. It is the ambition that produced the tail-chasing. If it is ever wanted, it is its own
  RFC, layered on top of this one, not a precondition of it.

- **A dependency-free, hand-rolled format.** Rejected. "No dependency" cannot coexist with
  "type-ignorant" and "faithful user types": to serialize a user type without a library, framec
  must generate code that inspects the type, which is exactly the per-type branching the
  type-ignorance boundary forbids. The dependency-free flat format could only ever do scalars,
  and did so by violating that boundary. "No dependency" was never an RFC requirement; it was an
  implementation impulse, and it is retired here.

- **One mechanism for all targets.** Rejected. Static and dynamic languages genuinely differ in
  whether the runtime can supply a value's type identity. Forcing a single mechanism means either
  carrying a type tag on static targets that do not need it (and re-introducing the collision
  problem it creates), or withholding it from dynamic targets that do. The two-regime split is
  not a hybrid of convenience; it is the shape of the problem.

- **Building our own serializer to beat the per-language libraries.** Rejected as infeasible and
  unnecessary. For a single language, the language's own serializer is the state of the art;
  framec's leverage is the Frame-specific frame around it, not the marshalling inside it.

## Migration

This RFC **supersedes** [RFC-0053](rfc-0053.md), [RFC-0054](rfc-0054.md), and
[RFC-0055](rfc-0055.md), and retires the cleanroom persistence roadmap. Those documents are
marked deprecated and **MUST NOT** be used as the basis for new work.

For existing cleanroom code: the Rust backend adopts `serde` (replacing the hand-rolled flat
format and its per-type branches); the Python backend's out-of-band envelope, escaping, and
closed-world registry are **kept unchanged** — they are the Regime B mechanism this RFC blesses;
the Java and C backends' scalar flat formats are **transitional** and are to be replaced by their
regime's serializer (Java) or the C decision above (C). No Frame source changes.
