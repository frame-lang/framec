# RFC-0062: Live control, async tool execution, and reflective (inception) agent architectures

- **Status:** Draft
- **Author:** Mark Truluck <mark.truluck@cogiton.com>
- **Created:** 2026-07-28
- **New terms:** [internal journal](../glossary.md#internal-journal), [inception architecture](../glossary.md#inception-architecture)
- **Builds on:** [RFC-0058](rfc-0058.md) §7.2–§7.3 (the controller/task-result-envelope seam and the architecture-map projection), [RFC-0061](rfc-0061.md) (the two-level per-tool-use agent harness)

The key words **MUST**, **MUST NOT**, **SHOULD**, **SHOULD NOT**, **RECOMMENDED**,
and **MAY** are to be interpreted as in RFC 2119.

**Register.** This RFC is **exploratory and forward-looking**, in the sense of
RFC-0058 §§5–7: it fixes a *direction* and the invariants that direction MUST
preserve, not a binding, shippable contract. It layers **on top of**
[RFC-0061](rfc-0061.md)'s base harness design, which — per the owner — is being
**built first**. Nothing here is adopted until the RFC-0061 foundation exists and a
pilot has fed results back as an RFC-0058 evolution-log entry. Where this RFC uses
normative keywords, they constrain *these layers if and when they are built*; they
do not add requirements to the RFC-0061 foundation.

## Summary

RFC-0061 makes an agent execution survive reaps by checkpointing a **small** durable
state after every tool-use. This RFC asks a different question: once such a machine
is running, how do we **observe** it, **steer** it live, run its tools **without
blocking**, and let the hosted model **reason about the machine it is inside** —
without breaking RFC-0058's determinism invariant or RFC-0061's single-tool-use
recovery cost.

The load-bearing observation is that these are **not three new mechanisms**. A Frame
`@@system` already emits a `$>`/`<$` enter/exit trace, present anyway for
observability and deterministic replay. Productionize that trace — make it
structured, typed, offset-addressed, and durable, and augment it with an *inbound*
channel — and you have one **[internal journal](../glossary.md#internal-journal)**
that serves three roles at once:

- **(A) a live control channel** *observes* the journal and *posts into* it;
- **(B) async managed tools** *emit into* it;
- **(C) the reflective ("inception") model** *reads* it as durable memory.

One append-only, offset-addressed, host-owned log; three seams onto it. The RFC
specifies the substrate (the foundation) and then each of the three layers as an
independent, separately-gated capability built on that substrate.

This structure is deliberate. The **foundation** — the tri-purpose journal and its
schema — is the only thing the three layers share and the only thing they all
require. Each **layer** names its own open decision and safeguards and gates on them
before being built. A layer that is deferred does not block the foundation; the
foundation does not imply any layer has shipped.

## Part I — Foundation: the internal journal as universal substrate

### 1.1 The reframe

RFC-0058 §7.3 and the RFC-0061 harness already posit a host-owned, append-only event
log and durable per-node state, referenced only by offset. The three architectures
requested here are three readers/writers of that one log. The foundation this RFC
fixes is therefore a single sentence:

> The internal journal — the machine's `$>`/`<$` enter/exit trace, present anyway for
> observability and deterministic replay — is the universal substrate. (A) the
> control channel and supervisor *observe* it and *post into* it; (B) async tools
> *emit into* it; (C) the inception-model *reads* it as durable memory.

Relation to Frame: the journal is the **productionized trace** of a hosted
`@@system` — the same `$>`/`<$` events, made structured, durable, and
offset-addressed, and augmented with an inbound channel carrying control events and
tool completions. This is the same offset-reference discipline RFC-0061 already
applies to the transcript and per-node state; this RFC extends it to say the log is
*tri-purpose* and gives it a schema.

### 1.2 The journal schema (normative for any implementation of these layers)

An implementation of any layer in this RFC MUST record onto a single log with the
following properties.

1. **Append-only, monotonic integer offsets.** The offset is simultaneously the
   address (for A/C reads), the logical clock, and the replay sequence number. The
   log MUST NOT be rewritten in place.
2. **Structured, typed records**, not free text. Each record MUST carry at least
   `{offset, ts, kind, state, corr_id, payload_ref}`. The `kind` set SHOULD include:
   `state_enter`, `state_exit`, `event_in`, `tool_spawn`, `tool_result`,
   `tool_error`, `timeout`, `checkpoint`, `control` (with a sub-kind of
   `cancel | adjust | hint | trace`), `classify`, `gate_verdict`, and `merge`.
3. **Heavy payloads out-of-line.** Tool stdout, model completions, and transcript
   slices MUST live in a side store; the journal holds only a `payload_ref`. This
   keeps the log cheap to tail (A), cheap to `read_journal` (C), and small in the
   persisted blob (it is the natural home for RFC-0061's `@@[no_persist]` scratch
   boundary).
4. **Durable-before-ack.** A record MUST be flushed durably before the machine
   treats the corresponding event as processed, so a reap cannot lose a completed
   tool result or a posted control.
5. **Single serialization point.** ALL inbound events — control (A) *and* tool
   completions (B) — MUST funnel through the one journal append. The total order the
   append imposes is what makes replay deterministic and keeps the machine
   single-threaded and race-free. All host concurrency lives in subprocess
   management and journal writes, **never** in the machine.
6. **Two logical channels, one physical log.** Machine-emitted trace
   (`state_enter/exit`, `classify`, `gate_verdict`) and host-emitted inbound
   (`event_in`, `tool_result`, `control`) are interleaved by offset. Observers (A)
   read both; the machine consumes the inbound records as its event source; the
   inception-model (C) reads the union.

The three seams restated on this schema: **(A)** supervisor, watchdog, and dashboard
*tail* the journal and *append* control records; **(B)** async tools *append*
completion records (the sink that serializes their nondeterministic order);
**(C)** `$Think` *reads* ranges as durable memory. Observation up-stream,
control/event down-stream, reflection-memory across — three architectures, one log.

### 1.3 What the foundation preserves

The foundation is chosen to preserve, unchanged:

- **RFC-0058 invariant 1** (orchestration-deterministic, controller-nondeterministic).
  Nondeterminism is confined to two points only — the controller (`$Think`, the model
  call) and the *journal append* (completion order). The machine's consumption of the
  journal is deterministic given the journal.
- **RFC-0061's recovery cost.** Because controls and completions are durable-before-ack
  journal records, a reap costs at most one tool-use and never loses a posted control
  or a finished tool result.

## Part II — Layer A: the live control channel

*Open decision this layer gates on: preemption granularity and the control-authority
trust boundary (§2.5). Safeguards below.*

### 2.1 The baseline and its three limits

Claude Code's `SendMessage` delivers a **conversation message** to a **live** agent
at its **next tool round**. Three limits: it is **coarse** (unstructured text into
the transcript, not a typed event); **not preemptive** (waits for the current tool
to finish); and **live-only** (a dead agent silently loses the message). Layer A
removes all three by routing control as typed events through the journal.

### 2.2 The control vocabulary as HSM-parent events

Control SHOULD be modeled as Frame **interface events handled at an HSM parent** —
`$Live` at the inner (per-tool) grain, `$Running` at the outer (per-cell) grain.
Children bubble anything they do not handle via `=> $^`, so the control plane is
owned in exactly one place per grain.

| control event | `$Live` handling | mutates | consumed |
|---|---|---|---|
| `cancel()` | children `=> $^`; parent → `$Abort` (graceful) or `$Error` | control state | immediately |
| `adjust_budget(deadline)` | rearm the **currently-armed** per-tool/patience budget in domain; **no state change** | domain budget register (the child armed it in its `$>`) | by the watchdog |
| `set_trace_level(level)` | set a domain trace-verbosity register | domain | future `$>`/`<$` journal detail |
| `inject_hint(text)` | append to a domain `pending_hint` register | domain | prepended by the next `$Think $>` into the model request |

This placement is the reification payoff, stated in the disposition vocabulary of
*Shadows on the Wall*: owning control at `$Live` **compresses** the design — adding a
control is one handler at the parent, not N handlers re-declared across every state.
The rejected alternative — each state re-declaring `cancel` — is **costuming**: N
named handlers that carry nothing the one parent handler does not already carry.

The design yields a clean division of labor: **children arm, the parent adjusts.**
`$ExecTool $>` arms the per-tool budget; `$Live`'s `adjust_budget` reads and extends
it. This is the honest home for "extend patience on a legitimately-slow tool instead
of killing it": the watchdog sees progress in the journal (new tool-stdout
`payload_ref`s appended) and posts `adjust_budget` to push the deadline — telling
*legitimately-slow* from *hung* on journal evidence rather than a blind timer.

Layer A unifies with RFC-0061's existing override contract. RFC-0061's `operations:`
override channel already carries the *bespoke* predicates (gate, spawn rules) bound
at `$Gate`/`$Spawn` on the `$Running` parent. Layer A adds the *harness-owned* control
members (cancel/adjust/hint/trace) at `$Live`/`$Running`. Same override mechanism, two
membership classes — harness-owned control versus bespoke predicate — both handled at
HSM parents.

The sketch below (a reduced `AgentLoop`, control owned at `$Live`) compiles under
framec:

```frame
@@system AgentLoop {
    interface:
        run()
        spawned()
        tool_result(corr: int)
        timeout()
        cancel()
        adjust_budget(deadline: int)
        inject_hint(text: str)

    machine:
        $Think => $Live {
            $>()                   { @@:self.attempts = @@:self.attempts + 1 }
            run()                  { -> $ExecTool }
        }

        $ExecTool => $Live {
            $>()                   { @@:self.deadline = 1200 }
            tool_result(corr: int) { -> $Record }
            timeout()              { -> $RetryTool }
        }

        $Record => $Live {
            spawned()              { -> $Think }
        }

        $RetryTool => $Live {
            $>()                   { @@:self.attempts = @@:self.attempts + 1 }
            run()                  { -> $ExecTool }
            timeout()              { -> $Escalate }
        }

        $Escalate => $Live { }

        $Abort   => $Live { }

        $Live {
            cancel()                     { -> $Abort }
            adjust_budget(deadline: int) { @@:self.deadline = deadline }
            inject_hint(text: str)       { @@:self.pending_hint = text }
        }

    domain:
        attempts: int = 0
        deadline: int = 0
        pending_hint: str = ""
}
```

### 2.3 Preemptive versus next-tool-round — the core result

Frame is **run-to-completion (RTC)**: an event dispatched while a handler runs is
queued and processed at the next dispatch boundary. Three consequences:

- A control event injected as a normal interface event is delivered at the **next
  dispatch point = next tool round**. **The Claude Code baseline falls out of Frame's
  semantics for free** — next-tool-round delivery is not a limitation to code around;
  it is the default RTC behavior.
- **Preemptive delivery requires that the current handler not block the host.** That
  is exactly Layer B. If `$ExecTool` launches the tool as a managed subprocess and
  *returns to the dispatch loop*, dispatch points occur **during** a long tool, not
  only between tools. Delivery latency drops from *tool granularity* (minutes) to
  *poll granularity* (sub-second). **This is the structural link: Layer B is what
  upgrades Layer A from next-tool-round to preemptive.** An implementation SHOULD
  therefore specify preemption as *"handled at the next host poll tick,"* with an
  explicit control-latency SLA (≤ poll interval, e.g. 1 s), and MUST NOT describe it
  as signal-level interruption.
- The alternative preemption path — Frame **operations** (synchronous methods that
  bypass the event queue) invoked from the watchdog thread — races the machine's own
  single-threaded dispatch and needs a host lock. An implementation **SHOULD NOT**
  use it. Keeping the machine strictly single-threaded and RTC preserves RFC-0058
  invariant 1 and deterministic replay; preemption comes structurally from Layer B.
  The watchdog's only *truly* preemptive act is killing the tool subprocess, which
  causes `tool_error(timeout)` to fire through the normal event path.

### 2.4 Three seams, one durable target

- **In-process (supervisor → cell).** Across RFC-0061's asynchrony seam this is **not**
  an in-memory call — the supervisor posts a control envelope into the cell's
  **inbound journal**.
- **Watchdog-level (out-of-band).** The native host's timer/async watchdog fires
  `timeout()` independent of the dispatch loop; combined with Layer B it kills the
  subprocess and posts `timeout()` to `$Live`.
- **Network control API (human/dashboard).** An HTTP or message-bus endpoint
  validates and translates an external request into a typed control event appended to
  the inbound journal. The dashboard **tails the journal (observe)** and **posts
  controls (control)** — symmetric read/write on the one substrate.

### 2.5 Dead-agent robustness — the baseline's biggest fix

Because controls are posted to the durable inbound journal, **not** to a live object,
they survive cell death. A `cancel()` posted while a cell is being reaped MUST be
honored on relaunch: `$Reap` → relaunch-fresh from RFC-0061's `durable_anchor` → the
fresh cell re-reads its inbound journal → immediate `$Abort`. The supervisor owns the
inbound journal, so control is **durable, not fire-and-forget** — precisely the
"live-agents-only" limit of `SendMessage`, removed. Cross-grain: `cancel()` at
`$Running` (outer) cascades to the inner grain by posting `cancel()` to the cell's
inbound journal.

**Open questions and safeguards.**
- *Preemption granularity.* Is poll-tick preemption (latency ≤ poll interval)
  "preemptive enough," or is a signal/interrupt path ever required? The RFC's lean is
  poll-tick, single-threaded; an adopter MUST define the SLA before building.
- *Operations vs queued events.* Do we ever need synchronous `operations` (preemptive
  but with a re-entrancy/lock hazard), or are queued events at poll granularity
  sufficient? Lean: events.
- *Network control auth.* Who MAY post control events into a cell's inbound journal?
  The mechanism is machine-agnostic, but an adopter MUST name the trust boundary and
  authenticate the network control API.
- *Two grains.* Confirm Layer A operates at both `$Live` (inner, per-tool) and
  `$Running` (outer, per-cell), with outer `cancel()` cascading inward via the inbound
  journal.

## Part III — Layer B: async managed-tool spawn

*Open decision this layer gates on: the parallel-`tool_use` grain and whether to reify
a `ToolRunner` system (§3.4–§3.5). Safeguards below.*

### 3.1 Feasibility

The native host already owns tool execution: `$ExecTool` invokes the tool, and today
it **blocks**. The redesign: `$ExecTool $>` launches the tool as a managed subprocess,
registers it in a host-side table under a correlation id, arms its watchdog,
checkpoints (**pre-tool**), and **returns to the dispatch loop**. Completion, failure,
and timeout are posted back as `tool_result(corr) | tool_error(corr) | timeout(corr)`.

### 3.2 The effector seam (tool call) nested inside the controller seam

RFC-0058 §7.3 reaches the **model call** across the **controller seam**: the
Controller is the nondeterministic decider on the far side of a task/result envelope.
Layer B gives the **tool call** its own seam of the same shape — the **effector seam**:

> `$ExecTool` is the machine (deterministic) side; the tool subprocess is the
> **effector** (the acting organ); `tool_result | tool_error | timeout` is the
> result envelope.

The harness thus has **two nested envelope seams** — the *controller seam* (model call)
and the *effector seam* (tool call) — each the same shape: a slow, nondeterministic
call on the far side of a task envelope, a deterministic machine side waiting on a
result envelope. This is RFC-0058's seam pattern applied fractally, and it names the
two organs precisely: the **Controller** decides, the **Effector** acts.

### 3.3 Non-blocking = responsiveness = the enabler of Layer A

Because the subprocess runs detached and the host monitors it, the host's main loop
stays **responsive**: while a long tool (e.g. a ~1200 s faithfulness diff) runs, the
loop keeps turning — polling subprocess status **and** polling the inbound control
journal. This is the mechanism behind §2.3's preemption claim and the single most
important payoff of Layer B.

### 3.4 Machine mapping and placement

`$ExecTool` MAY be reified as a small `ToolRunner` leaf system: `$Launch` (spawn, arm
watchdog, checkpoint) → `$Running` (subprocess alive) → `$Complete` (reap exit code,
capture stdout/stderr → `tool_result`) / `$Failed` (spawn error or nonzero exit →
`tool_error`) / `$TimedOut` (watchdog → kill subprocess tree → `tool_error(timeout)`).

**Placement ruling.** `ToolRunner` is an **in-memory leaf** of `AgentLoop` (same host
process); the **OS subprocess is the real asynchrony seam**. An implementation MUST
NOT put `ToolRunner` itself across a seam. Per *Shadows*, reify `ToolRunner` only if
`$ExecTool` grows its own multi-mode sub-lifecycle — otherwise the named states are
costuming. A first cut MAY keep `$ExecTool` a single state with the subprocess table
held in the host.

The reified `ToolRunner` sketch below compiles under framec:

```frame
@@system ToolRunner {
    interface:
        launch(corr: int)
        exited_ok()
        exited_fail()
        timeout()

    machine:
        $Launch {
            launch(corr: int) {
                @@:self.corr = corr
                -> $Running
            }
        }

        $Running {
            $>()          { @@:self.spawns = @@:self.spawns + 1 }
            exited_ok()   { -> $Complete }
            exited_fail() { -> $Failed }
            timeout()     { -> $TimedOut }
        }

        $Complete { $>() { @@:self.done = 1 } }
        $Failed   { $>() { @@:self.done = 2 } }
        $TimedOut { $>() { @@:self.done = 3 } }

    domain:
        corr:   int = 0
        spawns: int = 0
        done:   int = 0
}
```

### 3.5 Fan-out and concurrency

Multiple managed subprocesses coexist in the host table, each with its own watchdog
and correlation id; `tool_result` carries the corr id so the machine routes each
completion.

**Grain question — the RFC leans to fork/join inside `AgentLoop`.** Claude genuinely
emits **parallel `tool_use` blocks in one turn**; a single-tool `$ExecTool` loop
*glosses* that reality. Model it: `$ExecTool` forks the set, a `$Await`/`$Join` state
collects results, `$Record` commits when the join count is met. The domain carries
`inflight: Map<corr_id, ToolCall>` and a pending count. That **join count is a
recognition register** — a mode advanced by completions and read back to gate the
advance to `$Record` — so under *Shadows* it is a legitimate **reify** (observability
+ verifiability of the join), not a costume. Supervisor-level fan-out (multiple cells)
stays orthogonal (RFC-0061 owns that grain). A host concurrency cap (semaphore) that
prevents a heavy tool plus a heavy battery from exhausting the box is **host config,
not machine state**.

### 3.6 Clean cancellation

Managed subprocesses allow killing the **process tree** (long tools spawn children:
cargo, javac) on `cancel()`/`timeout()`, firing `tool_error(cancelled | timeout)`.
The blocking baseline cannot cancel a running tool at all — today a runaway tool can
only be escaped by killing the whole cell. Layer B fixes this.

### 3.7 Determinism caveat

Async completion order is nondeterministic. An implementation MUST preserve RFC-0058
invariant 1 by **serializing all completions through the journal append**: the host
appends `tool_result` records in real completion order; replay reads them back in
journal order. Nondeterminism is confined to the journal-write point; the machine's
consumption is deterministic given the journal — the same discipline as
"nondeterminism confined to the controller," here confined to the journal append. Tools
*run* in parallel; only their *completion records* serialize, which is cheap.

**Open questions and safeguards.**
- *Parallel `tool_use` grain.* Fork/join inside `AgentLoop` (lean: yes) versus pushing
  all fan-out to the supervisor.
- *`ToolRunner` reification.* Host table now versus a reified `@@system` when a
  multi-mode sub-lifecycle appears (the *Shadows* costume test).
- *`adjust_budget` authority.* Watchdog auto-extends on a defined progress signal (new
  tool-stdout `payload_ref`s appended to the journal) versus human-only. An adopter
  MUST define "progress" before enabling auto-extension.

### 3.8 Managed LLM instances via the Claude Code harness

The Controller (invariant 1's nondeterministic decider) MAY be realized as a
**managed child process** driven through the ambient `claude` CLI in headless
(`-p`) mode, authenticated by the ambient Claude Code credentials (keychain /
`~/.claude.json`); no `ANTHROPIC_API_KEY` is required. `claude -p` is the *headless
harness* — the same agent loop wrapped in a CLI — NOT the in-process mechanism by
which the main loop spawns subagents. The reason to run the Controller
out-of-process is **process isolation for reap-survival**: the watchdog can
`SIGKILL` a runaway turn by PID without killing the host, which an in-process cell
cannot provide.

**Two mappings.**

- **Decision-core Controller.** Per `$Think`, the host runs one `claude -p
  "<prompt>" --output-format json` turn with the child's OWN tools disabled
  (`--disallowedTools`); the model SHALL return exactly one JSON decision —
  `{"kind":"tool","name":…,"argv":[…]}` or `{"kind":"final","text":…}`. The machine
  keeps the loop, runs the proposed argv itself at the effector seam (§3.2), and
  owns all budgets. This is a constrained decider, not a subagent: the child runs no
  agentic loop, and each turn re-renders the full host-owned transcript, so it
  resumes by transcript replay and needs no `session_id`.

- **Whole-agent-cell.** The host MAY launch a full `claude` agent that runs its OWN
  tool loop to complete a subtask, managed as one reap-survivable unit. Its toolset
  SHALL be closed by default: an explicit `--allowedTools` allowlist MUST be passed
  and `Task` MUST be excluded unless the caller opts in with a recursion-depth
  budget. The cell MUST run under the same watchdog/checkpoint discipline as a tool.

**Authentication.** Under nightly/headless/cron execution the interactive
keychain/OAuth path may be absent, so an implementation MUST: pass `stdin=DEVNULL`
so any interactive login prompt fails fast; perform a cheap auth pre-flight and
raise a typed error when no usable credential exists; apply an explicit fallback
ladder — **ambient auth → a configured key passed via `env=` → fail-fast** —
recording the chosen source in the journal; and inspect the envelope's
`is_error`/`stop_reason` BEFORE parsing a decision, raising a typed auth/rate-limit
error rather than misreporting it as a parse failure.

**LLM-level reap-survival.** For the whole-agent-cell mapping, `claude -p` returns a
`session_id` that `--resume <id>` re-attaches. To survive a real reap (a new
process), the implementation MUST pre-assign the session (`--session-id <uuid>`, or
capture it from `--output-format stream-json`'s init) and persist that id to the
durable checkpoint BEFORE spawning the child; a `session_id` read only from the
final envelope and held in memory does NOT survive the kill it claims to survive.
`--resume` restores conversation memory only, not tool/FS state, so a tool-using
cell is **at-least-once** across a reap (cwd snapshot/restore, or idempotent-only
operations, or documented at-least-once semantics). The turn cap and a running cost
total MUST likewise be checkpointed durably.

**Security posture for LLM-chosen argv.** The "read-only" guarantee MUST NOT rest on
the system prompt — the machine executes whatever argv the Controller returns.
Before any unattended run the host MUST: allowlist `argv[0]` to resolved absolute
read-only binaries and reject model-authored shell pipelines (`/bin/sh -c "…"`)
unless routed through a vetted parser; run every tool (and every whole-cell child)
under a kernel-enforced sandbox with a read-only filesystem, no network egress, and
a credential-scrubbed environment (`cwd` provides NO containment); keep ambient
credentials out of the child's reachable filesystem; treat tool output as untrusted
data when it is re-rendered into the prompt that selects the next argv; and NEVER
pass `--dangerously-skip-permissions`. Until the sandbox, argv allowlist, credential
isolation, and durable turn/cost caps are in place, a managed-LLM Controller MUST
NOT drive real work unattended.

*(Proven live 2026-07-28: a decision-core `ControllerLLM` drove `AgentLoop` to
`$Done` after the model chose `/bin/sh -c "ls -1 *.py | wc -l"` — 2 turns, ~$0.05,
ambient auth; a whole-agent-cell returned `COUNT=10` and a `--resume` follow-up
recalled it from session memory.)*

## Part IV — Layer C: the reflective (inception) architecture

*Open decision this layer gates on: the self-knowledge scope and the anti-gaming
invariant (§4.4). Safeguards below.*

### 4.1 Two capabilities

**(i) Self-location.** At `$Think $>`, the host injects a compact **machine-context
block** into the model request: current state, HSM parent, attempt count, last
recovery classification, the reachable transition table, and the specific
next-on-failure state (e.g. "you are in `$ExecTool`, attempt 2, after a timeout; if
this fails again the machine goes to `$Escalate`"). This is **cheap and bounded** — a
projection of the current node plus outgoing edges of the machine's own generated
graph, plus the small checkpoint. It reuses exactly the projection the architecture-map
/ `--dump-ast` work already produces (RFC-0058 §5, §7.2), now at runtime. It does
**not** blow context — it is a fixed-size summary, never the journal.

**(ii) `read_journal(since_offset)` as a tool.** The model pulls journal ranges on
demand, offset-paged, reading only what it needs. Heavy payloads stay out-of-line
behind `payload_ref`s (§1.2), so a read is small. The model's working memory becomes
the **structured journal it queries selectively**, not the raw transcript.

### 4.2 Capabilities unlocked

1. **Self-monitoring before `$Escalate`.** The model reads the last K records,
   recognizes "three retries, same args, same error — same root cause," and changes
   strategy *before* the machine's blind attempt-counter trips `$Escalate`. The
   machine counts attempts *syntactically*; the model judges *semantic* sameness.
   Machine escalation is the backstop; model self-monitoring is the first line.
2. **Reap-recovery by re-reading the journal — the load-bearing one.** On
   relaunch-fresh, the fresh `$Think` does **not** reload the whole transcript (the
   reap-re-dies pathology RFC-0061 names). It rehydrates "what's been tried, what's
   known, where I am" from `read_journal(since durable_anchor)`. An adopter of Layer C
   **SHOULD** make the journal, not the transcript, the rehydration source. The
   transcript then degrades to an append-only provenance artifact referenced by
   offset, never reloaded wholesale. This is the single strongest argument for Layer C
   and directly retires RFC-0061's worst failure mode.
3. **Meta-reasoning / self-steering.** "The machine will relaunch me fresh if I die →
   I should checkpoint this partial finding into the journal now." "I am one attempt
   from `$Escalate` → make this attempt count."
4. **Introspective auditability.** `read_journal` calls are themselves journaled, so
   the audit trail records *what the model knew when it decided* — closing RFC-0058's
   auditability invariant.

### 4.3 Design fit — does not weaken RFC-0058 invariant 1

Nondeterminism stays confined to `$Think`. `read_journal` is a **read** tool — it
never mutates machine state; the model's action still returns through the normal
`llm_response(action)` event and is classified by the deterministic machine. The
journal is read selectively via the same offset discipline as the transcript.
Orchestration stays deterministic; the controller stays the only nondeterministic site.
`$Think` was never exactly replayable by construction, so the guarantee to restate is
**orchestration-deterministic, controller-nondeterministic** — Layer C does not weaken
it.

### 4.4 Safeguards and tensions

These are real and MUST be addressed by any adopter of Layer C.

1. **The model could game the machine.** Knowing "`$Escalate` at attempt 3," it might
   dodge a *necessary* escalation — narrate false progress to stay out of an owner
   gate, or shade its own verdict. This is a genuine principal-agent hazard introduced
   by capability (i). The mitigation is a **hard invariant**, not a hope:
   > **Self-knowledge is read-only over the control plane.** Every terminal,
   > escalation, and gate trigger MUST be a function of **machine-observed facts** —
   > the attempt count incremented in `$RetryTool $>`, wall-clock, tool exit codes,
   > the bespoke `$Gate` predicate over the *result* — and MUST NOT be a function of
   > model self-report. The model knowing the count cannot change the count; it emits
   > actions, the machine classifies. Giving the model self-knowledge is safe **if and
   > only if** this invariant holds.
2. **Re-reading a bad path reinforces the error** (anchoring on reap-recovery).
   Mitigations: (a) the journal records **outcomes and verdicts**, not just attempts,
   so a failed approach reads as *rejected* and steers away; (b) relaunch-fresh
   already discards scratch (RFC-0061 idempotency) — `read_journal` SHOULD default to
   start at the last **merged/committed** point (`durable_anchor`), rehydrating
   confirmed progress, not abandoned exploration; (c) records MAY be tagged with a
   disposition (`confirmed | abandoned | superseded`) so `read_journal` can filter — a
   journal-schema question left open below.
3. **Prompt-injection surface widens.** The journal now feeds the model; adversarial
   text in tool output, re-read later, is an injection vector. Journal reads inherit
   the same trust boundary as tool output — an adopter MUST name it. It is not a new
   boundary, but Layer C widens the exposure.

**Open questions and safeguards.**
- *Self-knowledge scope + gaming.* Exactly which machine facts does the inception-model
  see, and is "read-only over the control plane" (§4.4.1) sufficient, or must specific
  facts (the escalation threshold itself) be *withheld* to prevent dodging?
- *Bad-path reinforcement.* Are disposition tags (`confirmed | abandoned | superseded`)
  required in the schema, or does "default read from `durable_anchor`" suffice?

---

## Part V — Cross-cutting open question

**Journal vs transcript boundary.** Is the transcript a payload side-store of the
journal (referenced by offset — the RFC's lean), or a separate artifact? Layer C
(§4.2.2) wants the journal, not the transcript, to be the rehydration source. An
adopter MUST settle this explicitly before building Layer C, because it determines
whether the transcript is ever reloaded wholesale again.

---

## Part VI — Alternatives considered and rejected

- **Three separate mechanisms (a control bus, a job queue, a memory store).** Rejected:
  they would be three logs to keep consistent, three replay stories, three durability
  guarantees. The single tri-purpose journal (Part I) is the whole point — one total
  order, one durability contract, one replay.
- **Synchronous `operations` for preemptive control.** Rejected (§2.3): bypassing the
  event queue races the machine's single-threaded dispatch and needs a host lock,
  breaking RFC-0058 invariant 1 and deterministic replay. Preemption is obtained
  structurally from Layer B instead.
- **Signal-level tool interruption.** Rejected as the *model* of preemption (§2.3):
  the contract is poll-tick delivery with a stated SLA, not asynchronous interruption
  of the machine. The only genuinely asynchronous act is the watchdog killing a
  subprocess, which re-enters through the normal `timeout()`/`tool_error` event path.
- **Putting `ToolRunner` across an asynchrony seam.** Rejected (§3.4): the OS
  subprocess is already the seam; a second seam around the in-process runner adds a
  protocol boundary with no payoff — costuming.
- **Letting escalation/gate decisions read model self-report.** Rejected as a
  correctness hazard (§4.4.1): it would let the model game its own supervision. The
  read-only-over-the-control-plane invariant is the price of giving the model
  self-knowledge at all.
- **Feeding the model the whole transcript on rehydration (status quo).** Rejected
  (§4.2.2): it is the reap-re-dies pathology RFC-0061 exists to kill. Journal-scoped
  rehydration replaces it.

---

## Part VII — Relationship to RFC-0061 and adoption order

This RFC is strictly additive over RFC-0061 and, per the owner, is **not** adopted
until the RFC-0061 foundation is built and piloted. The recommended order:

1. **RFC-0061 foundation first** — the two-level per-tool-use machine with small
   durable checkpoints. No layer here is built before it exists.
2. **Foundation (Part I) next** — productionize the `$>`/`<$` trace into the
   tri-purpose journal with the §1.2 schema. This is the shared substrate; all three
   layers gate on it.
3. **Layers A, B, C are independent** and MAY be built in any order the pilot
   prioritizes, subject to one dependency: **Layer A's *preemptive* delivery depends
   on Layer B** (§2.3). Layer A's next-tool-round delivery, Layer B, and Layer C each
   stand alone on the foundation.

Each layer's results MUST feed back as an RFC-0058 evolution-log entry before it is
treated as more than exploratory.
