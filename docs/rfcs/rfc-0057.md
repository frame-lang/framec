# RFC-0057 — The Compiler

- **Status**: Draft (design; nothing built against it yet)
- **Author**: Mark Truluck
- **Scope**: The architecture of the rebuilt framec — its passes, its trees, its IR, and the rules
  each pass may and may not rely on. This is the document the rebuild executes against.
- **Implements**: [RFC-0056](rfc-0056.md) (the principles) and [RFC-0056.1](rfc-0056-1.md) (the
  descent). Those say *what must be true*. This says *what the compiler is*.
- **Does not change the language.** `if`/`while` remain native; the grammar is unchanged. That is
  what makes the existing corpus a valid specification (§7).

---

## 1. Summary

framec is rebuilt as a compiler with **one tree, built once, that covers every byte** — Frame
constructs and native code as sibling nodes — a **symbol table that resolves types, not just names**,
and passes that are **pure functions** over that tree. Emission is a one-way fold; nothing reads text
the compiler produced.

The old compiler keeps working throughout. The new one earns its way in against the existing corpus
(§7). **We never have a broken compiler, and we never cut over on a promise.**

---

## 2. What is actually wrong today (the one-paragraph version)

framec has an AST of the system *skeleton* and **no AST of handler bodies**. Below the handler's
opening brace it is a flat segment stream with native code as an opaque string. So every downstream
pass re-derives structure by reading text — its own output, or the user's — and **sixteen confirmed,
shipped bugs came from exactly that**. It is not a collection of mistakes; it is one missing tree,
observed sixteen times.

Two corollaries the architecture must answer directly:

- The compiler **scans the same bytes three times** (parser, then `enrich_system_metadata`, then
  codegen) and reconciles the results **by positional index**. The two recognizers have already
  diverged — one knows 21 `@@` forms, the other 6.
- The **assembler** stitches text, so it must grep its own output to find the `package` clause. It
  has no tree to ask.

---

## 3. The pipeline

Eight passes. Each takes an immutable input and produces a new value. **No pass mutates an earlier
pass's output; no pass re-derives what an earlier pass knew.**

```
  source bytes
      │
 [1]  SEGMENT ──────── island grammar. Split the file into ordered items:
      │                Native | Pragma | System | Efsm.  EVERY BYTE COVERED.
      │                Spans only. Nothing is interpreted.
      ▼
 [2]  DELIMIT ──────── per-target @@system machine. For native regions: block
      │                structure, statement boundaries where the target makes them
      │                lexically evident, and where each Frame construct sits.
      │                DELIMITED, NEVER INTERPRETED.  ← the pass framec never had
      ▼
 [3]  LEX ──────────── Frame islands only. Native spans are NOT lexed.
      │
      ▼
 [4]  PARSE ────────── FileAst: items in source order, recursively total.
      │                Handler bodies are STATEMENT LISTS in which native statements
      │                are nodes with spans — not gaps.        ← THE BODY AST
      ▼
 [5]  RESOLVE ──────── symbol table: names AND types, per compilation unit.
      │
      ▼
 [6]  VALIDATE ─────── pure AST walks. No text probes. Every diagnostic carries a span.
      │
      ▼
 [7]  LOWER ────────── FileAst → IR. The IR carries FACTS, never names to be decoded.
      │
      ▼
 [8]  EMIT ─────────── IR → target text. A fold. Terminal. Nothing reads it afterward.
      │
      ▼
      RENDER ───────── a fold over the FileAst: native items render from their spans,
                       system items render their emitted code. No stitching. No grepping.
```

Compare today: passes 1–4 are entangled and run **three times**; pass 2 does not exist; pass 5 has no
types; pass 6 reaches into pass 8; and the renderer is a text-stitcher that greps.

## 4. The tree

### 4.1 Total, recursively

```rust
struct FileAst { items: Vec<Item> }          // covers every byte of the file

enum Item {
    Native(NativeSpan),                      // the ocean — delimited, never interpreted
    Pragma(PragmaAst),
    System(SystemAst),
    Efsm(EfsmDeclAst),                       // a sibling ITEM; its COMPILER stays separate (§6)
}

// inside a handler body — also total:
enum Stmt {
    Native(NativeStmt),
    Transition(..), StateVarAssign(..), ContextData(..), SelfCall(..), /* … typed, ~20 */
}

struct NativeStmt {
    span:           Span,          // where it is
    logical_indent: u32,           // column relative to the handler-body base; RENDER's re-indent basis
    block_depth:    Option<u32>,   // nesting DEPTH — never block KIND. Some(_) only on targets
                                   // that consume it (see below); None where a lexer cannot know.
    refs:           Vec<FrameRef>, // sub-spans of $. / @@ Frame references INSIDE this statement
    literals:       Vec<Span>,     // string/comment/raw-literal extents RENDER must NEVER re-indent
    // NOTE: no `text` field. The text is the span. Reading it is what we are stopping.
    // NOTE: no `terminated` field. See D3.
}
```

**Invariant (P1.1), enforced as a property test:**

> `unparse(parse(src)) == src`, byte for byte.

If any byte is missing from the tree, that test fails. You cannot forget a byte, and you cannot
quietly widen a span. **Trivia — the whitespace and comments *between* statements — is covered too.**
That is the part everyone skips, and it is exactly where the terminator bug lives (a `;` spliced
*inside* a trailing comment).

This is distinct from codegen, which is a **different** fold (tree → target text). Two properties,
two tests.

### 4.2 The thing the old compiler could not express

Today two of Frame's three assignment forms get a statement-shaped node and the third gets nothing:

| Frame source | Today | Rebuilt |
|---|---|---|
| `$.x = 1` | `StateVarAssign` ✅ | typed node |
| `@@:data.k = 1` | `ContextDataAssign` ✅ | typed node |
| `@@:self.a = 1` | `ContextSelf` — a *reference*, with `.a = 1` falling out as untyped text ❌ | typed node |

Because that statement never existed, nothing could ask *"is it terminated?"* — so the compiler
searched its own emitted string for the last non-whitespace byte and landed the semicolon inside a
comment. **One missing node; a bug on seven backends.**

### 4.3 Every machine in this compiler is an `@@system`

framec is Frame's flagship user, and the compiler is built from **`@@system`** machines — the
segmenter, the delimiters, the skippers, the scanners. Not a mix of constructs; one construct.

That is only coherent as of now, because `@@system` finally has both things a scanner needs:

- **borrowed, positioned input** (RFC-0056 P9 / #209 — landed on all 16 targets; measured zero-copy
  and linear by the descent battery). Before this, a positioned probe copied the whole buffer on every
  call, scanning was O(n²), and *that* is why the scan logic was hand-rolled into native loops and the
  mode ended up in a native local — which **is** the string-blindness bug family.
- **a real stack** — `push$`/`pop$`, and #211 fixed `push$ -> $State(args)` so it can actually
  *carry* a value. Which matters, because Python/GDScript statement delimitation needs an
  **indent-level stack**: a dedent must pop to a *matching* prior level, so the levels must be
  remembered, not counted. `push$ -> $Block(level)` is exactly that, and it did not work until #211.

**One construct hosts every machine in the compiler**, including the only one that genuinely needs a
stack. No split design.

**`@@efsm` is not part of this rebuild.** It is a separate construct with its own compiler (~40k LOC,
its own front end, its own AST, its own 17 backends) that **never opens a source byte**. It is on the
keep-and-do-not-touch side of §6. Its language work (the rename, certificates, the classifier) is a
different track and must not be entangled with this one.

### 4.4 Delimitation vs. interpretation — the line the whole design rests on

> **Opaque ≠ undelimited.**

framec **MUST NOT** know what a native statement *means*. It **MUST** know its **structure**.

But "delimit ≠ interpret" is not the clean binary it sounds like, and stating it loosely would build
the design on sand. The honest line has **three tiers**, and the delimiter is allowed exactly two:

| tier | knows | allowed? |
|---|---|---|
| **lexical** | what is a string, a comment, a bracket, a raw string, a template literal | **YES** — framec already has this (the 15 skippers) |
| **structural** | block nesting; where each Frame construct sits; a statement boundary *where the target makes one lexically evident* | **YES** |
| **semantic** | what the code *means* — its types, its names, its effects | **NEVER** |

And a statement boundary is **not always knowable**, which the design must accept rather than paper
over:

- **Go** inserts a semicolon at a newline *depending on the last token* — so its delimiter needs Go's
  **token classes**. That is a lexer, not a parser: tier 2, allowed.
- **Lua** has no statement terminator at all (`x = 1 y = 2` is two statements). Its boundaries are
  *grammatical*, not lexical. So framec **does not know them**, and `terminated` / statement bounds are
  honestly **`None`** there.

That is acceptable — and it is acceptable for a *reason*, not by concession: under **P8, framec never
adds, removes, or moves a native terminator.** It does not need to know one in order to leave it
alone. What it genuinely needs is **block structure** (to suppress unreachable code after a
transition, and to build the body tree) and **the position of every Frame construct**. Those are
lexical facts, in every target.

> **The contract, stated exactly:** the delimiter recovers **block structure and Frame-construct
> positions in every target**, and **statement boundaries only where the target makes them lexically
> evident**. Where it cannot, it says so — it does not guess. *A guess is what produced the bug
> family.*

The Oceans model is a promise about the *language*, not a licence to leave native code
unstructured — and conflating those is what produced every bug in §2. This has a name: Frame's
Oceans model is an **island grammar** (Moonen, 2001), and in an island grammar **the water is still
tokenized and delimited**. framec adopted the idea and skipped the part that makes it work.

**There are no exceptions.** `if`/`while` are not Frame constructs and never were (the parser has no
such keyword); `block_transform` was re-deriving framec's *own* undeclared syntax from text it
emitted. It is deleted (§6).

## 4.5 The tree is a CONTAINER, not a leaf — and why the first draft could not hold the language

Rev 1 of this RFC declared `NativeStmt { span, terminated, block_depth }` and boasted *"no `text`
field — the text is the span."* **That tree cannot represent code framec compiles correctly today.**
Both of these ship, and both work, on `4.6.0.26`:

```frame
let total = $.count + compute(@@:self.factor, 2) * 3;   // TWO Frame refs inside ONE native stmt
print(f"count is {$.count}")                            // a Frame ref inside a STRING LITERAL
```

Rev 1 had **no field for either**. The island-grammar literature this RFC cites says plainly that
**the water is still tokenized** — rev 1 quoted that and then stopped at *delimited*, which is not the
same thing. `refs` and `literals` are that correction. The same two fields independently fix the
string-literal re-indentation miscompile (B7 below) — RENDER must know literal extents in order to
not touch them — which is a third argument arriving at the same place.

> **DELIMIT emits a token stream. `NativeStmt` carries it. Content is still never read.**

---

## 4.6 Two invariants, not one — the round trip is degenerate on its own

`unparse(parse(src)) == src` has a trivial satisfying assignment: **classify the whole file as
water.** The round trip cannot distinguish *"understood the file"* from *"understood nothing."*

That is not hypothetical. **B6 below is exactly it**: a UTF-8 BOM makes framec classify an entire
`@@system` as native text, emit it verbatim, and exit 0. Round-trip holds *perfectly*. The compiler
understood nothing.

The failure that ships is not *forgetting a byte*. It is **classifying an island as water**. So:

- **P1.1a — Coverage (the round trip).** `unparse(parse(src)) == src`, byte for byte. Cheap; stops
  span-widening and dropped trivia. **Necessary, and weak.**
- **P1.1b — Island coverage (the dual, and the one with teeth).** For every offset at which a Frame
  construct exists, the tree has a Frame node. Enforced as (a) a **granularity snapshot** — the
  per-handler statement count and kind sequence, blessed per fixture — and (b) a **differential**
  against the incumbent recognizer during the strangler period.
  **A file that parses to a single Native item is an ERROR, not a success.**

## 4.7 DECISIONS (Mark, 2026-07-12)

**D1 — Block DEPTH, never block KIND.** The tree records *how deep* a native statement nests. It
never records *what kind* of block encloses it. Only two consumers exist, and neither cares about the
kind: **unreachable-code suppression** after a transition's implicit `return` (Java, essentially
alone — the only target where dead code is a *compile error*) and **Python/GDScript indentation**.
Both want a number. Counting `{`/`}` tokens (or INDENT/DEDENT) yields it; *"is this an `if`"* never
enters. **`block_depth` is therefore scoped to the targets that consume it** and is honestly `None`
elsewhere — which is what dissolves Ruby, where `x = 1 if y` (no `end`) and `if y … end` are the same
token sequence and no lexer can depth-count. Ruby does not consume the field, so Ruby never needs it.

**D2 — Exact-name resolution for system-typed fields, plus a real diagnostic.** framec resolves
`kid: Child`. When a field's type text *contains* a known system name inside a target wrapper —
`Rc<RefCell<Child>>`, `Optional[Child]`, `Child?`, `*Child`, `shared_ptr<Child>` — framec does **not**
parse the wrapper. It emits a diagnostic naming the situation and telling the user to declare
`kid: Child` and let the backend wrap. **Zero type grammars.** (Rejected: parsing 17 type grammars —
tractable, but the camel's nose. Deferred: a Frame sigil `kid: @@Child`, which would make resolution
lexical *by construction*; revisit if the diagnostic proves annoying in practice.)

**D3 — `terminated` is DELETED.** Under P8 framec never adds, removes, or moves a native terminator,
so **nothing reads this field**. It was also the *only* thing dragging Go's automatic-semicolon-
insertion keyword table into the delimiter — the one field that made the hard target hard was the
field with no customer. Rev 1 declared it (with fine doc comments citing P4/P6/P8) and **no code
anywhere ever wrote it**; it was permanently `None`. That is the third instance of the same pattern in
this codebase (cf. `HandlerEntry.body_statements`: written at three sites, read at none).
**RULE: name a consumer for every field on a node, or the field does not exist.**

**D4 — Fail-fast now; error recovery deferred.** The parser bails on invalid source. Revisited when
the VS Code extension needs a tree from mid-edit (broken) source. **Recorded as a known future cost:**
retrofitting error recovery touches the parser's shape, so this is a deliberate debt, not an oversight.

**D5 — `--dump-ast` is built FIRST, before the first delimiter.** It is not an output feature; it is
**the test oracle for passes [2] and [4]**. The argument for it is this RFC's own §2: *the only way to
see what framec understood is to read emitted target code — which is why all sixteen bugs hid.*
Building the tree before the dump tool would reproduce that exact condition inside the rebuild.

**D6 — Java is the first backend, not Python.** Java has the simplest possible delimiter (C-family:
braces and `;`, one text-block wrinkle) and is the **only target that exercises three of the sixteen
bugs at once** — the statement terminator, `strip_java_unreachable` (#177), and `java_await_rewrite`
(#205). Python was the wrong choice for the reason this RFC itself supplies: it is the one genuine
*stack* customer for DELIMIT and the target where the indentation contract bites hardest, so it would
mean debugging the hardest delimiter and the first backend simultaneously — and the flagship
terminator win is *invisible* on it (Python is one of the five targets the bug never affected).

**D7 — RESOLVED: framec LEXES native code. It never parses it. Not ever.**

The claim under test was: *framec never needs the STRUCTURE of a native expression, only its EXTENT
and the sub-spans of the Frame refs inside it.* Two adversarial hunts **killed it** — and killed the
proposed repair with it. Both converged on the same principle.

- **Arity (#218).** framec splits `-> $S(a, b)` on top-level commas. But in C++, `a < b, c > d`
  (two args — comparisons) and `std::map<int, int>()` (one arg — a generic) are the **same token
  shape**. To split them, framec must know whether `std::map` *names a template*. That is **name
  lookup over the user's native types**. A lexer cannot do it — **and neither can a parser**: C++'s
  own grammar cannot, which is exactly why C++ has the `template` disambiguator keyword. Yet 13 of
  16 backends are already correct, because they **never split at all** — they hand the raw blob to a
  variadic and let the *target compiler* do it.
- **Precedence (#213).** framec splices `$.x` into expressions it does not parse. That is sound
  **only if the expansion is an atom**. C# emitted a bare cast — a non-atom — and the splice silently
  re-associated: compiled clean, exit 0, **wrong answer**. The repair is not to parse the surrounding
  expression. It is to **parenthesize framec's own output**.

> ### The principle
> **framec never needs to know the structure of native code. It needs to emit output that does not
> care.** And before asking *"lex or parse?"*, ask the prior question: **"does framec need this fact
> at all, or is it re-deriving something the target compiler already knows better?"**
> Arity: no. `terminated` (D3): no. Native expression structure: no. **Three for three.**

**Why this is not a cost argument, and must never be written as one.** The reason framec must not
parse native code is **not** that seventeen grammars are expensive. It is that **the capability
itself is the hazard**: if framec holds a parse tree of the user's native code, some pass will
eventually read it, and no type will stop it — and the moment a pass depends on native *semantics*,
framec is coupled to seventeen evolving language semantics forever. That is RULE 1 violated at the
root: *a pass may interrogate a node about facts **framec** put there, never about facts the **user**
put there* — and a native parse tree is nothing but facts the user put there.

And the capability question settles it independently of cost. Is there any fact framec legitimately
needs that **only** a native parse tree can supply? Block depth: lexical. Literal extents: lexical.
Frame-reference positions: lexical. Terminators: deleted (D3). Arity: not computed. Wrapped type
names: ruled out (D2). **Nothing remains.** The lexer is not a compromise. It is **complete** for the
set of facts framec is entitled to know — and a parser would buy exactly the capability we have
decided we must never use.

## 4.10 P14 — THE ATOM INVARIANT (new principle; promote to RFC-0056)

> **Every Frame-reference expansion MUST be an ATOM in the target grammar** — an identifier, a
> literal, a parenthesized expression, or an unbroken postfix chain (`a.b`, `a[i]`, `f(x)`, `x.(T)`)
> rooted at one of those. Any expansion whose **head is a prefix operator** (C-style cast, `*` deref,
> `!`, `-`, `await`), or that contains a **top-level binary or ternary operator**, MUST be wrapped in
> the target's grouping parens.
>
> Falsifiable form: for expansion `E` and every target, all of `f(E)`, `-E`, `E.m()`, `E[i]`,
> `a*E+b` MUST parse with `E` as a single operand.

This is the invariant that makes splicing-without-parsing **sound**. It is the load-bearing
precondition of D7: framec is only entitled to ignore the structure of the surrounding native
expression because its own output cannot interact with that structure.

**It has been breached three times** (C# cast, C cast, C `Boxed` deref) and each breach shipped.
Java, Kotlin, Swift, Dart, C++ and Go satisfy it; C# and C did not.

**Enforcement is by TYPE, not by review.** Review has now failed three times, in the same place, on
the same rule. The single collapsed expander returns an `Atom`, a newtype whose *only* constructors
produce atomic text — a cast cannot be built except through a constructor that parenthesizes it. A
future seventeenth backend then **cannot** reintroduce this class of bug, because rustc will not
compile it. (RFC-0056 P5: *types, not review*.)

**Corollary — lvalues are a different type.** `((int) m["x"]) = 1` is invalid C#, so the atom rule is
a rule about **reads**. Assignment targets need their own type with its own constructors. A single
`String` for both is precisely how the two expanders drifted.

---

**D8 — the root fix, not the symptom fix.** #213/#220/#221 are three symptoms of **one** disease:
`state_var.rs::expand_state_var` and `expression.rs::expand_state_vars_in_expr` are **two
implementations of one concept** (#222), and they have drifted four ways. Patching each backend arm
to agree is a workaround. **The fix is to delete one of them** and give the survivor a return type
that makes the invariant unrepresentable-to-violate.

---

**D7 (superseded — original wording kept for the record):** The claim under test is: *framec never needs the STRUCTURE of a native
expression, only its EXTENT and the sub-spans of the Frame refs inside it.* Mark's challenge stands —
*"I don't know why we don't parse! all 5 Frame statements are separable from native; the only issue is
Frame assignments of a native expression."* An adversarial hunt for a counterexample is running
(argument-splitting hazards; splice/precedence hazards). **If a counterexample survives, we build
native expression parsers. If none does, the lexer is earned.** Nothing is built until this resolves.

## 4.8 §4.2's flagship example was WRONG — P8 wins

Rev 1 §4.2 argued that `@@:self.a = 1` should become a **typed Frame statement node**, and that the
missing node caused the terminator bug on seven backends.

**That contradicts P8, and P8 is right.** `@@:self` is a *read-only reference*, not a mutation. So
`@@:self.a = 1` is a **native assignment with a Frame reference spliced into it** — precisely what
`NativeStmt.refs` (§4.5) now models. If it were a Frame *statement*, then by P8's own rule — *Frame
statements are framec's, and framec MUST terminate them* — framec would owe it a terminator in all 17
targets, which P8 says is portability-fatal (Go's ASI).

The consequence is uncomfortable and must be stated: **the node was not missing — the
auto-terminator was the bug.** The corpus (`_canonical/08_lifecycle.frm`), which hand-writes the `;`,
was **right all along**. This decides the shape of `Stmt`, so it is recorded here rather than argued
later. *(Bearing on the #173 fix, which added the `;`: revisit under P8.)*

## 4.9 Bugs found while attacking this design (all in the WATER)

Reproduced on `4.6.0.26`. The census said sixteen. Attacking the architecture added nine more, and
**every one is in the water** — the layer this RFC says is unstructured. Three are **silent
miscompiles** (exit 0, wrong program). They are the acceptance fixtures for pass [2].

| # | input (legal target code) | result |
|---|---|---|
| **B6** | UTF-8 **BOM** at file head | **SILENT** — the entire `@@system` is emitted as native text; no class generated. **exit 0** |
| **B7** | a multi-line string literal in a handler body | **SILENT** — `normalize_indentation` strips the margin from lines *inside the literal*; **the user's string has a different VALUE at runtime than in their source**. **exit 0**. Violates verbatim passthrough — an architectural boundary |
| **B8** | `print(f"…{@@:self.factor}")` | **SILENT** — emits `{:self.factor}`; the `@@` is swallowed. Broken Python. **exit 0**. (`unified.rs:487`: *"full @@ parsing in interpolation is rare"*) |
| B9 | JS/TS `let re = /[}]/;` | legal code **rejected** |
| B10–B13 | Ruby `=begin…=end`, `%w[}]`, heredoc; PHP heredoc | legal code **rejected** — and the *scanner* handles these (`php_skipper.gen.rs:378` calls `skip_php_heredoc`) while `body_closer/php.frs` does not, so the file dies before the scanner runs. **The two recognizers have diverged in the WATER, not just the islands** |
| B14 | Lua `local s = [==[ } ]==]` | legal code **rejected** |

B7 is the one to sit with: it means **"framec transforms nothing in user source — values verbatim"**
is not currently true. It is Python today; it is Rust `r#"…"#`, C++ `R"(…)"`, JS templates and Go
backticks tomorrow. It cannot be fixed without DELIMIT, because fixing it requires knowing which lines
are inside a literal — which is `NativeStmt.literals` (§4.5). The bug and the missing pass are the
same fact.


## 5. The IR

The IR's job is to make the old bugs **unwritable**, not merely absent.

### 5.1 Facts on nodes, never encoded in names

Today a method's generated *name* is the wire format of a missing field: `state_dispatch` knows it is
making a state handler and encodes that as the prefix `_s_`; then `async_wrap` **and** `backends/c.rs`
independently decode that prefix back into the fact — **with different prefix tables**. The naming
convention is an ad-hoc serialization of an enum nobody wrote down.

```rust
struct Method {
    role: MethodRole,          // Interface | Action | Operation | StateHandler | Machinery(..)
                               //   | Persist(..) | Ctor | Factory | AsyncInit | CasingDelegate
    emits_suspension: bool,    // "did *I* put an await/co_await in this body?" — only framec can
                               //  answer that, and only framec's answer is correct
    …
}
struct Class  { is_framework_helper: bool, input: Option<InputSpec>, … }
struct Unit   { required_imports: Vec<Import>, header_lines: …, scope: … }   // the renderer's input
```

**Names are for humans. Tags are for compilers.**

### 5.2 Two rules, enforced by types (RFC-0056 P5/P6)

1. **Never interrogate the user's text.** A pass may ask a node about facts *framec* put there; never
   about facts the *user* put there. **Every such predicate found in the census was a confirmed bug.**
   That is not a correlation — it is the rule being sound, and it is a mechanically checkable lint.
2. **Emission is one-way.** Once a node is rendered to text, **no pass may run over that text.** This
   is *not* implied by (1): the offenders mostly use `.lines()`, `.join()`, name substitution, or (in
   one case) a perfectly principled dogfooded lexer over framec's own output. A pass that tokenizes
   framec's own output with an impeccable machine is *still* re-deriving structure framec threw away.

Enforcement is structural, not cultural: **`EmittedText` and `NativeText` are distinct types whose
APIs do not expose `contains` / `find` / `rfind` / `starts_with` / `ends_with` / `split` / `replace`.**
The compiler literally *cannot* ask text a structural question. The single named boundary where they
can be opened is the delimiting machines of pass [2] — the only place framec legitimately reads text
it never parsed.

Three purges enforced this by review. All three failed. **A rule that can only be checked by grep is
not enforced; it is hoped for.**

## 6. Reuse — the honesty test

"Reuse what is useful" is where a rebuild goes wrong, and the failure mode is not retyping too much.
**It is grafting the old shape back on under the banner of reuse.**

Two very different things get called "the backends":

- **their knowledge** — Swift needs keyword escaping; C needs `_Generic` float dispatch; C++ needs
  `suspend_never` / `suspend_always`; Java does async at the interface boundary only. Every one cost a
  real toolchain run to find. **This is the treasure — and it is mostly *executable*** (57 RFCs, 6,141
  fixtures, 32 issue-named regression tests), not code.
- **their structure** — 17 hand-written match arms over an IR with no `MethodRole`, with
  `is_framework_helper` bolted on, and facts encoded in names. **This is the disease.** During the P9
  port, *the same bug appeared independently in four backends* and *two more stored a field before the
  instance existed*. Six identical mistakes across sixteen hand-written arms. That is not
  carelessness; it is what a 16-arm structure does to any fact threaded through it by hand.

**Reuse the first. Re-derive the second.** If we "reuse the backends" by keeping their match arms, we
have rebuilt nothing.

| Component | LOC | Disposition | Why |
|---|---:|---|---|
| **`@@efsm` compiler** (own parser, regex engine, validator, 17 backends) | ~40k | **KEEP** | Never opens a source byte. It has its own AST and its own front end. **It is the proof framec can host a real tree — it already does, in this construct.** Needs only the `@@efsm` rename + certificates (Track A). |
| **`machinery/`, `runtime`, `persist`, `graphviz`, `c_marshal`** | ~13k | **KEEP, re-typed to the new IR** | Consume AST/IR only; the census called them *exemplary*. `graphviz` has **zero** production text probes — proof a backend can be clean. |
| **17 backends** | ~15k | **ADAPT** — port the per-target *spelling*, re-derive the arms against the new IR | Knowledge is gold; structure is the disease (above). |
| **Front end** (segmenter, lexer, parser, native scanner) | ~22k | **REBUILD** | Two recognizers over the same bytes, reconciled by counting; no body AST. This is the hole. |
| **Validators** | ~6.5k | **REBUILD** | They reach *into codegen* to resolve names, and emit false diagnostics from a comma counter that cannot see brackets or strings. |
| **Assembler** | ~1.5k | **REBUILD as a renderer** | It stitches text, so it greps its own output. Given a tree, it is a fold. |
| **`block_transform` + output-block machines** | ~1k | **DELETE** | `if COND { }` is framec's *own undeclared syntax* — the Lua corpus never writes `then` once. Re-deriving one's own construct from emitted text. Kills #122/#135 by construction. |
| **The lexer's duplicate native recognizer** | ~0.7k | **DELETE** | The second of the two recognizers. |
| **`hack_census.py`** | — | **DELETE** | A grep policing greps. 76% false-positive; silent on all 16 bugs. Replaced by §5.2's types and the classifier. |
| **Erlang** | — | *already deleted* | |

**Corpus, RFCs, regression tests: KEPT ENTIRE.** They are the specification (§7), not implementation.

## 7. How the new compiler earns its way in

The old compiler stays shippable. The new one is built alongside and is **admitted only when it is
strictly better**, by a definition fixed in advance:

> **Acceptance.** The new compiler passes the **existing corpus** — 6,141 fixtures × 17 real
> toolchains, 240 snapshots, 32 issue-named regressions — **and turns the 11 adversarial fixtures
> GREEN**, which the current compiler fails.

That is falsifiable, and it is why the language must not change (it does not — §1): **an unchanged
language means the corpus is a valid spec.**

Two hard-won cautions, both already paid for:

1. **The corpus is not innocent.** `_canonical/08_lifecycle.frm` **hand-writes the semicolon framec
   should emit** — the corpus adapted to the bug. Byte-identity against a corpus that encodes the
   workaround would freeze the defect into the specification. Hence the 11 adversarial fixtures land
   *first*, and are **red today by design**.
2. **Differential testing is the ratchet, not the proof.** framec is a pure function and is verified
   deterministic (120/120), so old-vs-new can be diffed byte-for-byte. But those 6,141 fixtures caught
   **zero** of the 16 bugs. Byte-identity proves the new compiler is *not different*; only the
   adversarial fixtures prove it is *right*. **Prove equivalence, then break equivalence deliberately,
   one fix at a time.**

### Build order

1. **The tree and the delimiters.** Nothing works without pass [2]; it is also the pass framec has
   never had. Python/GDScript's delimiter is the one genuine stack customer (an indent-level stack —
   a dedent must pop to a *matching* prior level, so the levels must be remembered, not counted).
2. **One backend, end to end, one fixture family.** Python — dynamically typed, fewest confounds.
3. **Grow along the corpus.** The progress metric is *percentage of the corpus passing*, per backend.
   Not lines written.
4. **Cut over** when §7's acceptance holds. Delete the old.

## 8. Drawbacks

- **It is a rewrite of the front end, and rewrites fail.** The mitigation is that the *knowledge* is
  externalized to an unusual degree (57 RFCs, an executable corpus on 17 real toolchains) and that
  >52k LOC — the `@@efsm` compiler, machinery, runtime, persist, graphviz — **never opens a source
  byte** and is kept.
- **§5.2's newtypes are viral.** Removing `contains` from the text types will be felt on every line
  that touches text. **That friction is the point**, and it will still be resented.
- **"Adapt the backends" is the softest line in §6** and the most likely place the old shape sneaks
  back in. If a backend's new arm looks like its old arm, the rebuild failed there.
- **Two compilers coexist for a long time.** Cheap in tokens, expensive in discipline: every bug fix
  in the interim must be asked "does this belong in the old one at all?"

## 9. Unresolved (blocking, in build order)

1. **The compilation unit.** File? Module? The symbol table's scope, `@@import` resolution, and
   cross-file validation all hang on it. **Design against the *composition* cases** (a system holding
   another system; cross-file import) — the single-file case will mislead.
2. **Phases or queries.** A strict pipeline is simpler; a demand-driven model (Salsa, rustc) is what
   an incremental/LSP future wants. **Deciding late is expensive.**
3. **Where the new compiler lives** — a sibling module or a separate crate. A crate gives a hard
   wall (the old code *cannot* be imported by accident); a module is less ceremony. The wall is
   probably worth the ceremony.
4. **What the IR is, exactly.** §5 fixes its *rules*, not its shape. It deserves its own RFC once the
   tree is real, because an IR designed before its producer exists is a guess.
