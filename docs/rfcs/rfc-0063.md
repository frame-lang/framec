# RFC-0063: Heterogeneous controllers and the baked-in verifier

- **Status:** Draft
- **Author:** Mark Truluck <mark.truluck@cogiton.com>
- **Created:** 2026-07-28
- **New terms:** [heterogeneous controller](../glossary.md#heterogeneous-controller), [baked-in verifier](../glossary.md#baked-in-verifier)
- **Builds on:** [RFC-0058](rfc-0058.md) (the agent family), [RFC-0061](rfc-0061.md) (the two-level harness — AgentLoop + TaskOrchestrator), [RFC-0062](rfc-0062.md) (the internal-journal substrate / controller)

The key words **MUST**, **MUST NOT**, **SHOULD**, **SHOULD NOT**, **RECOMMENDED**,
and **MAY** are to be interpreted as in RFC 2119.

**Register.** This RFC is **exploratory and forward-looking**, in the sense of
RFC-0058 §§5–7 and RFC-0062: it fixes a *direction* and the invariants that
direction MUST preserve, not a binding, shippable contract. It layers **on top of**
[RFC-0061](rfc-0061.md)'s base harness, which — per the owner — is being **built
first**. Nothing here is adopted until the RFC-0061 foundation exists and a pilot
has fed results back as an RFC-0058 §10 evolution-log entry. Where this RFC uses
normative keywords, they constrain *these layers if and when they are built*; they
add no requirement to the RFC-0061 foundation.

## Summary

RFC-0061's `AgentLoop` confines all nondeterminism to a single pluggable
**controller**: `$Think` issues the model request and waits for an `llm_response`
event, and every other state is deterministic routing. This RFC observes that one
pluggable controller is not a constraint to *one* model — it is a socket. **Different
states MAY bind different controllers**, each a different model with a different
specialization, and the machine routes identically no matter how many models it
hosts. This is the [*Shadows*](../articles/Shadows_on_the_Wall.md) trichotomy read
off the harness directly: **the machine is the process; the models are values bound
at states; the check a verifier applies is a predicate.**

On that foundation the RFC bakes in one organ. A **`$Verify` state**, placed as the
last step before `$Done`, whose controller is a *separate* verifier model, independently
judges the worker's candidate result before the cell may report success — verdict
pass → `$Done`, fail → `$Recover` with the critique carried forward as the next
worker turn's hint. This is the machine-level formalization of the campaign's
hardest-won lesson, already reified at the *pipeline* grain by RFC-0058's independent
review: **the builder cannot self-certify; a separate organ must gate.** RFC-0063
pushes that principle down into the agent loop itself.

The structure is foundation-plus-layers. The **foundation** (§1) — one machine, many
controllers — is the only thing the rest requires, and it needs zero new machine
mechanism over RFC-0061. The **verifier organ** (§2) is one reified state on that
foundation. **Verifier independence** (§3) is a spectrum of controller *configs* on the
same socket, from an adversarially-prompted same-base model (available today) to a
dedicated fine-tuned verifier (future) — each a config swap, not a redesign, each
gating on its own honesty flag before being claimed.

## 1. Foundation — heterogeneous controllers

### 1.1 One socket, N models

RFC-0058 §7.3 makes the model call a **nondeterministic controller behind a task/result
envelope**, and RFC-0061 §4 confines that nondeterminism to exactly one state:
`$Think` issues the request in its `$>` enter and the machine waits for
`llm_response(action)`. The state is the *decide* side; the model is the *act* side;
`llm_response` is the result envelope. Nothing in that seam names *which* model
answers. The binding — model, system-prompt, and supplied context — is host config,
read when the host services the controller for that state.

It follows that **the controller is a socket, not a singleton.** The host holds an
controller table keyed by state; when the machine emits `state_enter` for an
controller-bound state, the host issues the request to *that state's* bound model. Two
controller-bound states emit indistinguishable `state_enter` records; the host's
dispatch to different models is the only difference. So one `AgentLoop` MAY host
several specialized models cleanly:

| state | role | controller binding |
|---|---|---|
| `$Work` | goal-specialized worker (RFC-0061's `$Think`/`$ExecTool` turn) | worker model + worker system-prompt |
| `$Verify` | independent verifier (§2) | verifier model + refute-prompt |
| `$Plan` *(optional)* | decompose the goal before working | planner config |
| `$Critique` *(optional)* | structured self-review feeding `$Work` | critic config |

A design under this RFC that binds more than one controller is a **[heterogeneous
controller](../glossary.md#heterogeneous-controller)** design. Adding, removing, or
swapping a model **MUST** be an controller-config change and **MUST NOT** require a
change to the machine's states, transitions, or events. The `state_enter` contract of
RFC-0062 §1.2 is unchanged; a heterogeneous design records the *bound role* as
controller config, not as a new record kind.

### 1.2 The trichotomy, read off the harness

The reason this composes cleanly is the [*Shadows*](../articles/Shadows_on_the_Wall.md)
§4 trichotomy, and stating it in that vocabulary is the whole design:

- **The machine is the process.** `AgentLoop`'s states and transitions route
  deterministically regardless of how many models are bound. This is a **REIFY**:
  compression (a handful of named modes replace scattered role-dispatch flags),
  observability (a role boundary is a state that survives a reap, not a program
  counter), verifiability (laws bind to the named graph — §2).
- **The models are values.** A bound model is an controller config — a *value* at a
  site — not a machine. It is **left latent** under *Shadows* §6.3's value plea: its
  engine (the routing machine) lives elsewhere. **Void condition** (the plea's
  reversal): if a single model invocation grows its *own* multi-mode sub-lifecycle —
  streaming phases, nested tool sub-calls carrying a recognition register — it
  **SHOULD** be promoted to its own `@@system`, the same void condition RFC-0061 §2
  and RFC-0062 §3.4 apply to the bespoke workflow and to `ToolRunner`. Until then,
  reifying "the worker model" as a state would be **costuming**.
- **The check is a predicate.** The verifier's judgment against the goal /
  definition-of-done is a *law over the candidate* — neither process nor data
  (*Shadows* §4.4). It is inert as a prompt and becomes a **constraint** only when
  bound at `$Verify`, where it gates the transition to `$Done`.

Because nondeterminism stays confined to the controller-bound states, **RFC-0058
invariant 1 is preserved unchanged**: orchestration deterministic and auditable, the
controllers the only nondeterministic sites. Heterogeneity widens the *set* of controller
seams; it does not add a nondeterministic site anywhere else.

## 2. The baked-in verifier organ

### 2.1 The organ

A **[baked-in verifier](../glossary.md#baked-in-verifier)** is a `$Verify` state
placed as the final step before `$Done`, whose controller is a *separate* verifier
model. On entering `$Verify` the host issues the verifier request — the worker's
candidate result, the goal / definition-of-done, and (optionally, per RFC-0062 Layer
C) a `read_journal` range as evidence — and waits for a `verdict` event. The verdict
routes:

- **pass** → `$Done` (the cell reports success up the result envelope);
- **fail** → `$Recover`, carrying the verifier's critique forward as the hint
  prepended to the next `$Work` turn (RFC-0062 §2.2's `inject_hint` register is the
  natural carrier).

An `AgentLoop` under this RFC **MUST NOT** transition to `$Done` except from a
verdict-pass at `$Verify`; the verifier organ, if present, is not bypassable on the
success path. This is a reachability law over the named graph, model-checkable exactly
as RFC-0061 §10's *every path to `$Merge` passes through `$Gate`*:

> **Every path to `$Done` passes through `$Verify`**, and **no `$Done` without a prior
> `verdict(pass)`.**

`$Verify` **REIFIES** on all three payoffs. *Observability:* the verdict is a named,
journaled step — a pass/fail is a state and a record, not a hidden boolean inside the
worker's last turn. *Verifiability:* the reachability law above binds to the graph.
*Compression:* one organ replaces the scattered, easily-omitted "and then check
yourself" that a single-controller loop leaves implicit. This refines RFC-0061 §12 open
decision #7 ("verify lives inside the cell; `$Gate` only adjudicates") from a
placement lean into a named state.

### 2.2 Why a separate organ — the evidence

The organ formalizes a lesson the byte-exact reverse-engineering campaign paid for
repeatedly: **a cell that both produces a result and certifies it certifies its own
blind spots.** The pattern recurred with the same shape — a builder self-reported
success that a *separate* gate then refuted:

- a storage-model change claimed **"byte-identical"** when the emitted bytes differed;
- a diagnostic claimed **`E419` "matched"** when the two representations diverged;
- a state-variable read described as a **"boxed deref"** when the target packs a C
  `int` in the pointer word (intptr-packed), so there was no box to deref.

In each case the producing party had no way to see the error *from inside the act that
made it* — the wrong claim and the wrong work shared one source. The separate gate
caught every one. RFC-0058 §4.6 already records this at the *pipeline* grain: "every
stage caught a defect the previous stage missed," and "the designer never certifies
its own work" (§4.3). RFC-0063 is that same principle pushed **inside the cell**: the
worker controller and the verifier controller are differently-purposed organs of one
machine, so the certification is structurally not the builder's to issue.

### 2.3 A Frame sketch

The organ is small. `$Work` is the worker turn (RFC-0061's `$Think`/`$ExecTool`
cycle, abstracted); `$Verify` is the organ; `$Recover` re-arms the worker with the
critique in `hint`. The host issues the **worker** model on `$Work` enter and the
**verifier** model on `$Verify` enter — the heterogeneous binding of §1.1 — while the
Frame body does only deterministic bookkeeping and routing. Verdict routing is native
`if` in the handler body (Frame has no transition guards; per RFC-0061 §4 this is a
predicate-in-force whose engine is the machine, left latent by design):

```frame
@@system WorkCell {
    interface:
        run()
        work_result(candidate: str)
        verdict(ok: int, critique: str)

    machine:
        $Work {
            $>()                        { @@:self.attempts = @@:self.attempts + 1 }
            work_result(candidate: str) { @@:self.candidate = candidate  -> $Verify }
        }

        $Verify {
            $>()                            { @@:self.checks = @@:self.checks + 1 }
            verdict(ok: int, critique: str) {
                if ok == 1:
                    -> $Done
                @@:self.hint = critique
                -> $Recover
            }
        }

        $Recover {
            $>() { -> $Work }
        }

        $Done { }

    domain:
        attempts:  int = 0
        checks:    int = 0
        candidate: str = ""
        hint:      str = ""
}
```

`$Work` and `$Verify` emit identical `state_enter` records; the host's controller table
sends the first to the worker model and the second to the verifier model. On a fail
verdict the critique lands in `hint` and `$Recover` re-enters `$Work`; on a pass it
reaches `$Done` — and there is no other edge into `$Done`. (Compiled to `python_3`
and exercised: `$Work → $Verify`, a fail routes back through `$Recover` to `$Work`
with the critique carried in `hint`, a subsequent pass reaches `$Done`; `$Done` is
reachable only via a pass verdict.)

## 3. Why separately-trained — correlated blind spots, and the independence spectrum

### 3.1 The argument from correlation

A single model that both *does* and *checks* shares its own blind spots with itself:
the error it cannot see while producing is the error it cannot see while reviewing,
because both readings run through the same weights and the same priors. Independence
is the whole value of the verifier, and independence is a *property of the config*,
not of the machine. Because the verifier is just an controller config on the §1 socket,
the machine buys **as much independence as the config supplies, at zero machine
cost** across the whole spectrum:

| # | verifier config | independence | availability |
|---|---|---|---|
| (a) | **same base model, adversarial role/prompt** — instructed to *refute*, default-to-reject-if-uncertain | *partial* (real, but correlated on shared priors) | **today** |
| (b) | **a different model** (different base, different training data) | more (uncorrelated architecture/data) | today, where a second model is available |
| (c) | **a dedicated fine-tuned verifier**, trained to *find divergences* rather than produce candidates | most (trained for the opposite objective) | **future** |

All three are `{model, system-prompt, context}` triples bound at `$Verify`. Moving
from (a) to (b) to (c) is a config change; **it is not a machine change, and this RFC
requires none.**

### 3.2 Honesty flag

**No fine-tuned verifier (c) exists today.** The near-term realizable form is (a):
same base model, adversarial role. That is a genuine but *partial* independence — the
RFC-0058 §4.6 review gate already demonstrates its force (refute-prompted reviewers
caught defects their same-family producers missed), so (a) is not a straw form; it is
the honest floor. But an adopter **MUST NOT** describe an (a)-config verifier as
having the independence of (c). The value of stating the spectrum is precisely that
(a) is a *config swap away* from (b) and (c): the machine built for (a) is the machine
that hosts (c) the day a fine-tuned verifier exists.

## 4. Composition with the two-level harness — two independent checks

The verifier organ sits at the **inner** grain; RFC-0061's `$Gate` sits at the
**outer** grain. They are two *independent* checks, and keeping both is belt and
suspenders:

- **Inner — `$Verify` (the worker's own skeptic).** Inside the cell, the verifier
  controller judges the candidate *before* the cell emits a result envelope at all. Its
  authority is the goal / definition-of-done as the verifier model reads it.
- **Outer — `$Gate` (the bespoke DoD predicate).** In `TaskOrchestrator`, the
  bespoke gate predicate adjudicates the *result envelope* the cell emitted (RFC-0061
  §5, §9). `$Gate` MAY itself be backed by its own verifier controller — a second,
  outer heterogeneous binding — or stay a deterministic predicate; either way it is a
  separate organ from the inner one, adjudicating separately.

This is the machine-level expression of RFC-0058's specialized agent **family**:
worker and verifier are not two separate agents passing files, they are two
differently-purposed **controllers within one machine**, and the family's
"reviewer-is-not-the-producer" rule (RFC-0058 §4.3, §8 independence) becomes a
structural property of the state graph rather than a process discipline an operator
must remember. A defect that slips the inner verifier still faces the outer gate; a
defect the outer gate is not shaped to see may have been caught inner. The two checks
gate different artifacts (candidate vs. result envelope) with different authorities
(verifier judgment vs. bespoke predicate), which is exactly why keeping both pays.

## 5. Tensions and safeguards

These are real and an adopter **MUST** address each before relying on the organ.

1. **A same-model verifier can rubber-stamp.** An (a)-config verifier sharing the
   worker's priors may agree by default. Mitigation is **adversarial framing as a hard
   part of the config**: the verifier system-prompt **MUST** instruct refutation
   (find the reason this is wrong) and **SHOULD** default to *reject-if-uncertain*, so
   silence or ambiguity routes to `$Recover`, not `$Done`. A verifier that passes on
   "looks fine" is misconfigured.
2. **The verifier's own false-rejects create retry churn.** An over-eager verifier
   sends good candidates back to `$Work`, burning turns. Mitigation: the `$Verify →
   $Recover → $Work` cycle **MUST** be bounded by the same attempt ladder RFC-0061 §4
   gives every recovery — a bounded `attempt`, then `$Escalate` to an owner gate.
   Unbounded verify/rework is the failure mode; the ladder is the backstop.
3. **The extra model call per candidate has a cost.** A verifier turn is a whole
   additional controller invocation. It is **justified when the cost of a wrong success
   is high** — a wrong merge into a byte-exact reverse-engineering baseline is exactly
   that case, which is why this campaign is the motivating one. An adopter **SHOULD**
   gate the organ on that cost asymmetry: where a wrong `$Done` is cheap to detect and
   undo downstream, the deterministic `$Gate` alone MAY suffice and the inner organ
   MAY be omitted.

A cross-cutting safeguard inherited from RFC-0062 §4.4: if the verifier reads the
[internal journal](../glossary.md#internal-journal) as evidence, its verdict is still
a **function of machine-observed facts and the candidate**, never of the worker's
self-report about its own success. The read-only-over-the-control-plane invariant
holds: the verifier judges the artifact, it does not take the worker's word for it.

## 6. Alternatives considered and rejected

- **A deterministic-predicate-only gate (RFC-0061 `$Gate` alone, no verifier
  controller).** Insufficient *alone* for the motivating case. A fixed predicate catches
  exactly what it was written to check; the campaign's failures were *semantic
  over-claims* — "byte-identical" that wasn't, "matched" when representations diverged,
  "boxed deref" of an unboxed value — that no bounded predicate anticipated, because
  anticipating them is the judgment the verifier supplies. Kept as the **outer** check
  (§4), not as the whole story. Where wrong-success is cheap, though, the predicate
  alone is the right, lighter choice — the §5.3 cost gate.
- **A single-model self-check (the worker reviews its own candidate before `$Done`).**
  Rejected as the primary gate: correlated blind spots (§3.1). The model cannot see,
  while reviewing, the error it could not see while producing. A self-check is a
  `$Critique` refinement of the *worker* config, useful as a first pass, but it is not
  an independent organ and **MUST NOT** be counted as the verifier.
- **External human review as the per-candidate gate.** Rejected as the *per-candidate*
  mechanism: it does not scale to every candidate and re-introduces the human as a
  synchronous bottleneck. The human belongs at **escalation** — RFC-0061's
  `$Escalate` / `$OwnerGate`, RFC-0058 Step 4's owner gate — reached when the bounded
  verify/rework ladder (§5.2) exhausts, not on the common path. Human review is the
  backstop the machine escalates to, not the organ that gates every result.
- **A separate verifier *agent* passing artifacts to a worker *agent* (two agents,
  not two controllers).** Rejected as heavier than the problem: it re-introduces a
  process boundary, its own transcript, and its own reap surface for what is one
  additional controller turn inside a machine that already survives reaps. Two
  controllers in one `AgentLoop` gets the independence with one checkpointed machine —
  RFC-0058's domain-focus principle (P-B) does not force a split here, because these
  are two *roles of one loop*, not two jobs.

## 7. Invariants preserved

A design under this RFC **MUST** honor:

1. **RFC-0058 invariant 1** — nondeterminism confined to controllers; orchestration
   deterministic and auditable. Heterogeneity widens the set of controller-bound states;
   it adds no nondeterministic site elsewhere (§1.2).
2. **RFC-0061 recovery cost** — the verifier organ adds states, not a second machine;
   a reap in `$Verify` costs at most one tool-use and resumes from the pre-controller
   checkpoint, exactly as `$Think`/`$ExecTool` do.
3. **Every error/terminal transition is a named state** — `$Recover`, `$Escalate`,
   `$Done`; no silent drop of a fail verdict.
4. **Type/config, not machine, carries model identity** — a bound model is controller
   config; framec emits no per-model code and the machine is model-agnostic
   (consistent with the Oceans Model: the host owns the models, the machine owns the
   routing).
5. **Read-only over the control plane** (RFC-0062 §4.4) — the verdict is a function of
   the candidate and machine-observed facts, never of worker self-report.
