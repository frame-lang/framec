# RFC-0053: Faithful persistence — reflection-driven typed restore

- **Status:** Draft
- **Author:** Mark Truluck <mark.truluck@cogiton.com>
- **Created:** 2026-07-06
- **Builds on:** RFC-0012 (persist stress testing), RFC-0016.1 (`@@[no_persist]`), RFC-0049 (one portable semantic, per-target mechanism)

## Summary

`@@[persist]` promises that a saved snapshot restores the system's state. Today
that promise holds for scalars, lists, and dictionaries but silently breaks for
a domain variable whose value is an instance of a user-defined type — and it
breaks *differently* on each target: some reconstruct it perfectly, some crash
at save, some restore a shape that has lost its type. This RFC makes **faithful
restore the guaranteed default**: save-then-restore MUST reproduce the domain
state exactly, for any type, on every target that can persist at all. It
specifies the mechanism (reflection-driven typed serialization), the security
posture that mechanism requires, the per-target reach and its ceilings, and the
long-term direction of a framec-owned wire format that removes the remaining
dependence on each target's serialization library.

## Motivation

A persistence feature that works *under some circumstances* is worse than one
with clearly stated limits, because the failure is invisible until runtime and
inconsistent across targets. A program that compiles cleanly and round-trips a
counter will, with a one-line change to hold a small value type instead, either
keep working, throw at save, or quietly restore a type-erased shape — depending
only on which language you emitted. That is the single most surprising thing a
user can hit, and it undermines trust in the whole feature.

The asymmetry has a precise cause. A snapshot is a *typeless* document: the
common wire format (JSON) carries only objects, arrays, strings, numbers,
booleans, and null — never the identity of a user-defined type. Whether a
restore can rebuild a typed value therefore depends entirely on where the *type*
comes from at restore time:

- **Targets whose deserializer is handed the type as a schema** (the statically
  typed languages) reconstruct user types transparently: the deserializer walks
  the declared type's fields and rebuilds the object. The type *is* the recipe.
- **Targets whose deserializer is handed nothing** (the dynamically typed
  languages, whose libraries decode into generic containers) cannot rebuild a
  typed value at all — they hand back a bare map. The strictest of them refuses
  to even *save* an unknown object and raises at save time; the more permissive
  ones save a best-effort shape and lose the type on the way back.

So the gap is a property of the *format's* type erasure crossed with each
*library's* willingness to bridge it — not a fundamental limit of the language.
Every dynamically typed target can, in fact, both read a value's type from a
live object (reflection) and rebuild an instance from a type plus its fields.
The feature simply has to *do* that instead of delegating to a library that
won't.

A fix has to achieve three things: (1) restore is faithful for any persistable
type, with no silent lossiness; (2) the behavior is the same story on every
target, so there are no per-language surprises; and (3) it does not reintroduce
the security hole that the earlier move away from a code-executing serializer
deliberately closed.

## The contract

The key words **MUST**, **MUST NOT**, **SHOULD**, **SHOULD NOT**, and **MAY**
are to be interpreted as described in RFC 2119.

### Faithfulness

For any system carrying `@@[persist]`, and for every domain variable not marked
`@@[no_persist]`, a save immediately followed by a restore into a fresh instance
MUST reproduce that variable's value such that all subsequent observations are
indistinguishable from the original. This holds regardless of the variable's
declared or inferred type, including instances of user-defined types and
arbitrarily nested graphs of them, on every target that supports `@@[persist]`.

Faithfulness is the **default and only** behavior. There is no opt-in required
to get it and no silent degradation permitted. A target that cannot meet it for
a given program MUST fail at compile time with a diagnostic (see *Ceilings*),
never at runtime and never by restoring a lossy shape.

### Mechanism: reflection-driven typed serialization

Frame expresses one portable semantic — *"reproduce this value's type and
state"* — and each backend emits it in its native mechanism (the same
one-semantic / per-target-mechanism discipline as RFC-0049). For a target whose
serialization library already reconstructs user types from a schema, that native
mechanism is the library call it already makes; nothing changes. For a target
whose library does not, the backend MUST emit reconstruction itself:

- **On save**, the generated code captures, for each value it cannot represent
  as a native scalar/array/map, the value's **type identity** and its **fields**,
  using the target's runtime reflection. The type identity travels *in the
  snapshot* alongside the fields.
- **On restore**, the generated code reads the type identity, resolves it to a
  type, and rebuilds an instance from the saved fields.

This is a single, generic pass — it introspects whatever object it is given and
never contains a branch per user type. It therefore preserves the existing
principle that framec emits no per-user-type persistence code; the reflection is
uniform.

### Closed-world reconstruction (security posture)

Reconstruction reintroduces a capability the typeless-document model did not
have — restore now *builds a type the snapshot names* — so its blast radius is
bounded normatively:

1. Restore MUST resolve a snapshot's type identity only against types **defined
   within the generated program's own compilation unit** (its own module /
   namespace / file, including framec's generated runtime types and the user's
   in-source types). It MUST NOT resolve a type by arbitrary name against the
   ambient global environment, and MUST NOT be able to name an imported or
   library type.
2. Restore MUST rebuild an instance **without invoking the type's constructor**
   or any other user code path the snapshot could direct — it allocates the
   instance and sets its fields directly (allocate-without-init).
3. Consequently, a corrupt or hostile snapshot MAY cause one of the program's
   *own* persistable types to be allocated with attacker-chosen field values,
   but MUST NOT be able to execute arbitrary code, import a module, or
   instantiate any type the program does not itself define.

This is a deliberate, bounded relaxation of the prior guarantee that restore
instantiates nothing a snapshot names. It is accepted as the cost of faithful
restore, and it remains categorically narrower than a code-executing serializer,
which permits arbitrary import and code execution on load.

The intent is the **opposite** of trusting the snapshot: restore treats a
snapshot as **untrusted input** and bounds what a hostile or corrupted one can
do. The residual blast radius is exactly points 1–3 above — a snapshot can cause
one of the program's own persistable types to be allocated with arbitrary field
values, and nothing more; it cannot escalate to code execution, module import,
or instantiation of any type the program does not define. A program that
restores snapshots from an untrusted source SHOULD authenticate or
integrity-check the blob where even that residual — arbitrary field values on
its own types — is a risk it must exclude.

### Reach and ceilings

Targets fall into tiers by how far the contract reaches natively:

- **Schema-deserializing targets** (the statically typed backends): already
  faithful; the library reconstructs from the declared type. No change beyond
  ensuring the declared type reaches the deserializer — including the case where
  a target is statically typed but its JSON library does *not* reconstruct, in
  which case the backend emits the reviver from the type it holds.
- **Reflective class targets** (the mainstream dynamic languages with a real
  class model): reachable in full. They expose a value's type and fields on
  save, allocation without construction, and closed-world name resolution on
  restore. One shared design covers them, expressed in each one's idiom.
- **Convention-only object targets** (a dynamic language whose "objects" are a
  base container plus a convention, with no first-class type identity): a
  user-defined *type* has no portable identity to capture. Here the contract is
  met by persisting the native container form; a program that asks to persist a
  by-convention "class" value that cannot be faithfully reconstructed MUST be
  rejected at compile time rather than restored lossily.
- **Host-object targets** (a target whose runtime provides its own object
  (de)serialization facility): reachable via that facility, subject to its own
  constraints, which the backend MUST respect or else reject at compile time.

Where a target cannot faithfully reconstruct a given program's persisted value,
the compiler MUST emit a diagnostic identifying the offending domain variable
and the reason, so the failure is caught at build time. A runtime `TypeError`,
a silent type-erased restore, or a partial object are all non-conforming.

## Examples

A small value type held in a domain variable round-trips with no user
boilerplate and no annotation required:

```frame
@@[persist(string)]
@@[save(save_state)]
@@[load(restore_state)]
@@system Body {
    interface:
        set_velocity(vx, vy)
        speed_x()
    machine:
        $Moving {
            set_velocity(vx, vy) { @@:self.velocity = Vec2(vx, vy) }
            speed_x()            { @@:(@@:self.velocity.x) }
        }
    domain:
        velocity = Vec2(0, 0)
}
```

After `save_state()` then `restore_state(blob)` into a fresh `Body`,
`@@:self.velocity` is again a `Vec2` with the saved `x`/`y` — not a bare map.
A nested graph (a domain variable holding a type that itself holds user-typed
fields) round-trips the same way, because the save pass tags every level and the
restore pass rebuilds every level.

## Alternatives

- **Reject non-native domain variables at compile time (only).** A diagnostic
  that a persisted value must be a scalar/list/map turns the silent runtime
  failure into a loud build-time one. Rejected as the *primary* answer: it makes
  the feature honest but not *faithful* — it pushes the modelling burden back
  onto the user and leaves persistence unable to do the obvious thing. The
  diagnostic is retained only as the ceiling behavior where faithful restore is
  genuinely unreachable for a target.

- **Reconstruct from a source-level type annotation alone.** Frame can annotate
  a domain variable's type, and the backend could rebuild the top-level type
  from that annotation. Rejected as insufficient: the annotation names only the
  outermost type; the field types of a user type live inside opaque native code
  the compiler never parses, so nested user-typed fields cannot be rebuilt from
  the annotation. It fails the "under all circumstances" bar. (Runtime field
  reflection, in contrast, recovers nesting without the annotation, which is why
  the mechanism above uses reflection rather than annotations.)

- **A code-executing serializer** (a whole-object serializer that stores a class
  reference and re-imports it on load). Reconstructs anything transparently, but
  by executing arbitrary code from the snapshot on load — the exact hazard the
  move to a typeless document removed. Rejected: it is target-locked, not
  cross-language, and a snapshot becomes an execution vector.

- **Require the user to supply per-type encode/decode hooks.** Faithful and
  safe, but not the default experience — it makes the common case (a small value
  type) carry boilerplate. Retained as a permitted *override* a user MAY provide,
  not as the baseline.

- **Embed the type name and resolve it against the ambient global environment.**
  Handles nesting generically but lets a snapshot name *any* reachable type,
  including imported ones — the code-executing serializer's hazard in a thinner
  disguise. Rejected in favor of the closed-world resolution above.

## Migration

Source-additive; no Frame source changes are required, and existing persisted
programs keep compiling. On the affected targets a snapshot's wire form gains a
type tag on non-native values, so a snapshot written by a newer compiler is not
guaranteed to be readable by an older runtime of the same program; snapshots are
already tied to a program's shape (topology is validated on restore), so this
extends an existing coupling rather than introducing a new one. The security
posture change (closed-world reconstruction) is documented at the persistence
boundary in the language reference.

### Forward-looking: a framec-owned wire format

The mechanism above still uses each target's serialization *library* for the
*encoding* (the bytes), while framec owns the *type/field capture* (the
reflection). The long-term direction is to remove the library dependence for the
encoding as well: framec emits its own serializer and deserializer over a
format it defines end-to-end. Because framec would then control the format
completely, it can also re-tighten the security posture with strict structural
validation on load. This is captured as direction, not committed scope; the
reflection mechanism and the closed-world posture stand on their own under the
present libraries.
