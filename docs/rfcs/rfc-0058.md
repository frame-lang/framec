# RFC-0058: The multi-agent development method — design, plan, execute, test under a falsifiable contract

- **Status:** Draft
- **Author:** Mark Truluck <mark.truluck@cogiton.com>
- **Created:** 2026-07-17
- **New terms:** none (see *A note on register*: the coined vocabulary here is process
  terminology defined in-document, not Frame-language vocabulary for the
  [glossary](../glossary.md))
- **Builds on:** RFC-0031 (post-release process — the precedent for a process RFC)

The key words **MUST**, **MUST NOT**, **SHOULD**, **SHOULD NOT**, **RECOMMENDED**,
and **MAY** are to be interpreted as in RFC 2119.

## Summary

This RFC specifies how framec development is carried out when the work is large,
long-running, and at risk of "declaring itself done when it isn't." The method
divides the work into four roles — **design**, **plan**, **execute**, **test** —
each carried by one or more specialized agents, and binds them with five
load-bearing principles: *done* is a mechanical predicate that can fail (never a
judgement); the party that judges the work is never the party that produced it;
the plan changes only through a recorded, evaluated log; anything touching a
project boundary escalates to the human; and reviewers try to *falsify* the work,
not confirm it. It is a **process** RFC: there is no Frame syntax here, and its
worked example is a real campaign rather than runnable source.

## Motivation

Long-running work — a subsystem rewrite, a self-hosting conversion, a multi-backend
feature — fails in ways that a single implementer, working alone or with an
unsupervised assistant, does not reliably catch. The recurring failure modes are:

- **Losing the goal under context pressure.** As a task stretches across many
  sessions, the working definition of "what we are building" drifts. Without a
  written, durable statement of the goal, the work quietly re-scopes itself to
  whatever the last few steps made convenient.
- **Declaring done when it isn't.** A green test suite is offered as proof, but the
  suite does not gate the thing that matters. The canonical instance is a compiler
  self-hosting conversion where every fixture *compiled* and the output was *wrong*
  — the suite proved the code ran, not that it was correct. "It compiles" and "the
  tests are green" are evidence only in proportion to what those tests actually
  constrain.
- **Large changes landing unreviewed.** A refactor that touches a load-bearing seam
  is merged because it is plausible and the author is confident. Plausibility is not
  review.
- **Silent drift between plan and code.** The plan says one thing; the code does
  another; no one recorded the divergence, so the plan stops being a description of
  reality and becomes fiction.
- **One party as both advocate and judge.** The implementer — human or AI —
  evaluates their own work. They are motivated to find it done. An advocate grading
  their own case is not an audit.

None of these is fixed by working harder or being more careful; care does not
survive context pressure, and self-review does not survive self-interest. They are
fixed *structurally*: by writing the goal down as a contract whose satisfaction can
be mechanically checked, and by separating the party that does the work from the
party that judges it. That is what this method institutionalizes.

## The contract

### A note on register

The [RFC style guide](STYLE.md) is written for **language** RFCs. This is a
**process/methodology** RFC, and three of its conventions adapt rather than apply:

- There is no Frame syntax to specify, so **Examples** below is a worked account of
  a real campaign, not Frame source. The runnable-sample rules (a `@@[target]`
  directive plus an entry guard) do not apply — no block here is meant to compile.
- **Migration** is *process adoption*, not code rewriting; it describes how a team
  starts using the method, and names no codemod because there is none.
- The coined vocabulary the method needs — *warden*, *guardrail*, *falsifiable
  Definition of Done* — is **process terminology, defined in this document**. It is
  deliberately *not* added to the Frame [glossary](../glossary.md), whose scope is
  the language and its runtime. This RFC's `New terms:` line is therefore `none`.
  (One prior term is reused, not redefined: a [differential *oracle*](#terminology)
  in the testing sense below is the standard software-testing "test oracle," which
  is distinct from the compiler [oracle machine](../glossary.md#oracle) the glossary
  defines. Where confusion is possible this document says "differential oracle.")

A one-line editorial judgement, recorded as requested: a durable process convention
like this would sit equally well as a `docs/` process guide; it is written as a
numbered RFC by request, and doing so has the benefit that its lineage and
supersession are tracked like any other design decision.

### Terminology (process terms, scoped to this RFC)

- **Role** — one of the four kinds of work: *design*, *plan*, *execute*, *test*. A
  role is a responsibility, not a person; one contributor MAY carry several, subject
  to the separation-of-powers rule below.
- **Agent** — a specialized, repo-versioned reviewer or author with a written brief
  that fixes its subject, its method, and what it must resist. Agents realize the
  roles.
- **Guardrail** — a standing, non-negotiable constraint on the work that no step may
  violate and no agent may waive (for example: *only the sanctioned construct
  performs recognition; the old path is deleted the moment the new one is proven; a
  capability the toolchain cannot express is surfaced as a blocker, never
  hand-rolled around*). Guardrails belong to the human.
- **Falsifiable Definition of Done (DoD)** — the goal restated as a conjunction of
  mechanical predicates, each of which can **fail** when checked by running or
  grepping. "Done" is the conjunction holding; it is never a judgement call.
- **Warden** — the agent that judges a unit of work against the falsifiable DoD. It
  verifies every predicate by running or grepping, cites the evidence, never
  rubber-stamps, and returns PASS only when every applicable predicate holds. A
  single failing predicate is a FAIL.
- **Warden gate** — a checkpoint at which the warden is consulted and its written
  verdict (PASS/FAIL plus findings) is recorded before the work may proceed.
- **Differential oracle** — an independent reference for correctness: the prior
  implementation kept alongside the new one, or a hand-computed expected value,
  against which the new work is compared. It MUST be independent of the code under
  test.

### The four roles

The method structures a body of work as a pipeline of four roles. The roles are the
**foundation** — every campaign runs all four. Domain-specialist reviewers
(codegen, persistence, release, style) are **layers** added to the design and test
roles per campaign, gated on the campaign actually touching their subject; a
campaign that changes no persistence does not add the persistence reviewer.

#### DESIGN

Before work is planned, the shape of the problem is settled by adversarial,
code-grounded critique. The design agents — an FSM/computational-machine architect,
a compiler architect, and the RFC author — do three things:

- **Classify the problem.** For each unit of work they answer "is this *structure*
  (data and its walkers), a *machine* (a recognizer/automaton), or *neither*?" and
  name the right tool. Mislabeling a first-token dispatch as a state machine, or a
  counter as a pushdown automaton, is caught here, not after it is built.
- **Ground every claim in the code and the toolchains.** A design assertion about
  how a target behaves is verified by generating and running, not asserted. A design
  built on a false premise about a backend is the most expensive failure, so design
  review hunts for it first.
- **Record what was rejected and why.** The alternatives and their rejection reasons
  are written down, as in any Frame RFC.

Design review is **adversarial**: the reviewer's job is to falsify the design, not
to bless it.

#### PLAN

The design is turned into a **living plan that is a contract**. A conforming plan
**MUST** contain:

1. **A falsifiable Definition of Done** — per-unit predicates (each converted
   capability is done iff *all* of a fixed list of mechanical checks hold) and
   campaign-level predicates (the whole effort is done iff *all* of a second list
   hold). Each predicate names how to *falsify* it. A plan whose "done" is a
   description of a feeling, rather than a predicate that can fail, does not conform.
2. **Fine-grained milestones with warden gates.** The unit of progress is small (in
   the reference campaign, one capability per commit). Named gates sit at the
   load-bearing transitions — at minimum a *parity* gate that MUST pass **before**
   the new path is wired into production (never wire a wrong machine) and a *landed*
   gate that MUST pass **after** the old path is deleted (never call a capability
   done with its predecessor still present).
3. **A recorded change protocol.** The plan changes only through an append-only,
   dated **Change Log**: each entry states *what* changed, *why*, *which
   DoD/guardrail/invariant it touches*, and *the alternatives considered*. A change
   is then evaluated (below) and its resolution recorded.
4. **An append-only Audit Log** of every warden verdict.

The plan is authoritative: where the plan and the code disagree with no Change Log
entry, that is **drift**, and drift is a defect (see *recorded change*).

#### EXECUTE

The implementer performs the work under the standing **guardrails**, in the
plan's small units — in the reference campaign, one capability per commit, landing
its source, its generated artifact, its seam, and its test together. The implementer
operates **within** the contract: it MAY make any decision the contract already
settles, and it MUST NOT make a decision the contract reserves — anything touching a
guardrail, the native/allowlist boundary, or scope escalates (below). The
implementer does **not** judge its own output; that is the warden's role.

#### TEST

Testing is a distinct role with two separated parties:

- **The test author** builds and **runs** the tests: a unit battery per unit of work
  (exhaustive over the forms it handles, plus edges, plus adversarial inputs, plus a
  deterministic fuzz/property generator), at least one end-to-end milestone test per
  milestone, and — where a prior implementation still exists — a differential harness
  comparing the new output to the [differential oracle](#terminology) at every
  position. Every test the author writes, the author runs; a test that was not run is
  not a test. The author labels each test as scaffolding (internal to the campaign)
  or promotable (a durable, behavior-level spec), but does **not** decide whether the
  milestone is done.
- **The warden** grades the work against the DoD, including whether the tests exist
  and are *strong* — a test that cannot fail is worse than none, because it
  manufactures false confidence.

The author *builds*; the warden *grades*. They are never the same party.

### The five load-bearing principles

Everything above rests on five principles. These are the normative core.

#### 1. Falsifiability — done is a predicate, not a judgement

Every gate **MUST** be a mechanical predicate that can fail, and it **MUST** be
verified by running or grepping, never by reading prose and believing it. "It
compiles" and "the suite is green" are admissible evidence only to the extent they
*constrain the thing that matters*: a suite that passes for any partition of the
input does not prove the partition is correct, and the plan **MUST** say plainly
which test is the correctness gate and which are merely necessary conditions. This
is the direct countermeasure to the compiles-but-wrong failure.

#### 2. Adversarial independence — the reviewer tries to falsify

Design reviewers and the warden **MUST** attempt to *disprove* the work, not to
confirm it. A correctness check **MUST** compare against an oracle that is
**independent of the implementation**: the prior code, or a hand-computed expected
value — never the implementation's own logic copied into the expected value. An
agent that cannot verify a predicate reports it as unverified (a pending FAIL), not
as PASS.

#### 3. The human owns the guardrails

Agents decide freely **within** the contract. Anything that touches a **guardrail**,
the **native/allowlist boundary** (what is permitted to remain outside the sanctioned
construct), or the **scope** of the work **MUST** escalate to the human; an agent
**MUST NOT** waive a guardrail, move something across the allowlist boundary, or
change scope on its own authority. A blocker — a needed capability the toolchain
cannot express — **MUST** be surfaced and escalated, and **MUST NOT** be
hand-rolled around.

#### 4. Recorded change — the plan moves only through the log

The plan **MUST NOT** change silently. Every change — a reordering, a deferral, a
new or removed sub-component, a discovered wrong dependency, a blocker, or any
deviation from the DoD or a guardrail — **MUST** be entered in the Change Log,
evaluated, and resolved as **ACCEPT** / **REJECT (with reasons)** / **ESCALATE**. A
change that touches a guardrail, the allowlist, or scope is **auto-ESCALATE** to the
human. At the landed gate the warden diffs code-reality against the plan; any
deviation with no Change Log entry **FAILS** the gate — it is either recorded as a
change or reverted. Drift with no entry is a defect.

#### 5. Separation of powers — the author of work does not judge it

The party that produces a unit of work **MUST NOT** be the party that certifies it
done. The warden is not the implementer; the test author builds the batteries and
the warden grades them; design is critiqued by reviewers who did not do the design.
One contributor MAY carry more than one role across *different* units of work, but
never both *produce* and *judge* the *same* unit.

## Examples

The method's reference campaign is a framec self-hosting conversion: replacing the
compiler's hand-written scanner byte-loops with generated Frame state machines, one
capability at a time, keeping each hand implementation in place as a free
byte-for-byte differential oracle until its replacement is proven and every consumer
is routed off it.

The worked instance is the first converted capability — an opaque-region skipper
(strings and comments). It shows every principle biting:

- **The plan carried a falsifiable DoD.** "Done" for the capability was the
  conjunction of predicates a machine can check: the generated artifact must
  regenerate byte-for-byte and stay identical across a rebuild; every residual native
  helper must be a fixed-size fact, not a smuggled loop; the differential test must
  agree with the oracle at every byte position over both curated *and* fuzz inputs;
  every production consumer of the old path must be rerouted or named-and-deferred;
  the old path must be deleted or its deletion assigned to a named later item; the
  suite must be green; the machine's claimed computational class must match its shape;
  and the whole thing must land in one atomic commit.

- **The warden's dry-run FAILED — on real predicates, not vibes.** Consulted at both
  gates, the warden returned FAIL with cited evidence: the differential test had *no
  fuzz generator*, so its correctness predicate was weaker than claimed; a grep found
  *surviving hand consumers* of the old path that the plan had not accounted for
  (the residual-consumer list was wrong — five, not three, including one in
  production and one belonging to an "already converted" component that was in fact
  not wired to production at all); and the artifacts were *uncommitted*, failing the
  atomic-commit predicate. Any one of these is a FAIL; the warden reported all three
  with file evidence rather than accepting the implementer's "it's essentially done."

- **The change protocol recorded the refinement instead of hiding it.** The correct
  response was not to loosen the DoD but to record a change. A Change Log entry noted
  that only one of the surviving consumers was genuinely extent-only and safe to
  reroute immediately; the other two were deferred, each to a *named owning item*,
  because rerouting them would have altered behavior on malformed input or discarded a
  policy distinction the extent alone does not carry. The deferral satisfied the
  "retired-or-named-deferral" predicate precisely because it named the owner; a
  deferral with no owning item would itself have been a FAIL. A separate change
  (narrowing target coverage) was **auto-escalated** to the human because it touched
  target coverage — a boundary an agent may not decide.

The lesson the instance makes concrete: the method *caught the lie early*. A
single-implementer flow would have shipped a green-but-under-tested skipper with a
live duplicate of the code it was meant to replace, and recorded none of it. The
warden gate, the independent oracle, and the recorded-change rule each removed one
of those outcomes.

## Alternatives

- **Single implementer, no agents.** One contributor designs, plans, builds, tests,
  and certifies. Rejected: it collapses separation of powers (principle 5) — the
  advocate grades their own case — and it has no structural defense against losing
  the goal under context pressure. It is exactly the configuration whose failure
  modes motivate this RFC.

- **Post-hoc review only** (build first, review at the end). Rejected: review that
  arrives after a large change has landed is too late to be cheap — the wrong machine
  is already wired, the old path already deleted or already duplicated, and the
  reviewer's leverage is gone. The parity gate exists *specifically* to run **before**
  wiring, and the landed gate **before** the capability is called done; end-only
  review has neither.

- **A plan without a falsifiable Definition of Done.** A roadmap of milestones with
  no per-milestone mechanical predicate. Rejected: "done" becomes a vibe. Nothing
  stops a milestone being declared complete on the strength of a green suite that
  does not gate correctness — the precise mechanism of the compiles-but-wrong
  failure. Falsifiability (principle 1) is not an add-on to the plan; it is what
  makes the plan a contract.

- **Agents that can approve their own work** (the implementer agent also returns the
  PASS). Rejected: it re-introduces the advocate-as-judge failure with a veneer of
  process. The warden's independence is structural — it does not write code, and its
  verdict is evidence-cited and recorded — precisely so that a persuasive
  implementer narrative cannot substitute for a passing predicate.

## Migration

This is process adoption, not a code change; there is no codemod and no breaking
change to any shipped behavior. A team adopts the method incrementally:

1. Write the goal as a **falsifiable DoD** before starting — per-unit and
   campaign-level predicates, each with a stated way to fail. If a "done" criterion
   cannot be made to fail mechanically, it is not yet a criterion.
2. Stand up the **warden** and the **test author** as separate parties from the
   implementer, and place at least the parity (pre-wire) and landed (post-delete)
   **gates**.
3. Open the append-only **Change Log** and **Audit Log**, and adopt the
   ACCEPT/REJECT/ESCALATE protocol with auto-escalation on guardrail, allowlist, and
   scope.
4. Add **domain-specialist reviewers** as layers only where the campaign touches
   their subject.

A team may adopt the roles without the specific agent roster; the roster is one
realization of the method, not the method itself.
