## 1. Summary

Development on this project is increasingly performed *with* and *by*
agents. This RFC is the living architecture of that agent workforce: a
family of **domain-focused agents** — each with one job, a structurally
enforced boundary, and a shared worldview — connected by a pipeline in
which a static **finder** recovers the
[latent machines](../glossary.md#latent-machine) in source, a **designer**
turns inventories into system architectures, builders build, and
independent gates judge. It records what is shipped, what is planned, and
the evidence behind each choice. It stays Draft while the architecture
evolves; changes land as dated entries in § 10.

The analysis capability is named in two tiers, and the names are
load-bearing throughout this document. **Local analysis** (§ 5): within one
scanned scope — a file, module, or single process — find the machines,
trace how they drive one another, and deliver the structure a designer
needs to re-architect that scope into system hierarchies. **Global
analysis** (§ 6): the advanced tier — relating systems *across* components,
packages, processes, wires, and threads. Global builds strictly on local:
it consumes completed local maps; it never replaces them.

## 2. Principles

- **P-A One worldview, one text.** Every agent in the family holds the
  latent-machine worldview and loads the canonical paper at engagement
  start. **Agent instruction files are packaging** — search heuristics,
  deliverable shapes, repository discipline — and MUST remain re-derivable
  from the paper (RFC-0059 P5/F3). When an instruction file and the paper
  disagree, the paper wins.
- **P-B Domain focus over omnibus.** One agent, one job, hand-offs named.
  Evidence: multi-role omnibus agents ran several times longer for no
  additional code-level findings; every narrow-charter agent in project
  history has been reliable.
- **P-C Structural boundaries, not stylistic ones.** An agent's constraint
  is enforced by its *tool set*, not its instructions, wherever possible —
  the static scanner has no execution tool at all. Make the illegal
  transition unrepresentable.
- **P-D The engagement is a machine; the intake brief is its init state.**
  The **intake brief** is the per-engagement task statement — target and
  boundary, purpose, deliverable shape, and depth. (It is distinct from
  the agent's standing instruction file, P-A's subject.) Every agent
  follows the intake protocol: a supplied intake brief is restated back
  ("brief as understood") so a mis-inference is visible; an absent one is
  answered *with a proposed intake brief* — each of those four fields
  pre-filled from a minutes-long survey of the actual target — never with
  unscoped work.
- **P-E Verified claims only.** Static agents ground every claim in
  file:line and mark execution-dependent facts "unverifiable statically."
  Dynamic verification (builds, test suites, predicate re-runs) is a
  separate domain with a separate role (the delivery warden, § 3).

## 4. The pipeline

The pipeline is itself a machine: its steps are states, its hand-offs are
transitions, and — by its own discipline — its error transitions are
named. Work flows forward through five steps; every failure verdict names
the step it returns the work to.

**Scope of the pipeline.** It governs **conversion units**: replacing an
existing hand-written scope with a designed, explicit system, the hand
code serving as the comparison baseline until it is deleted. A greenfield
design (no code being replaced) traverses Steps 2–4 with no terminal
ledger and no parity gate, since both exist to protect fidelity to code
being replaced.

### 4.0 Cast and artifacts

| Name | What it is | Where defined |
|---|---|---|
| intake brief | the per-engagement task statement (target, purpose, deliverable, depth) | P-D |
| Machine Inventory | the finder's census of a scope's machines | [glossary](../glossary.md#machine-inventory); RFC-0059 P3 |
| architecture map | the inventory organized for reassembly (exploratory) | § 5 |
| design record | the designer's deliverable: target architecture + verification plan + terminal ledger | § 4.2 |
| terminal ledger | every terminal of the replaced code, each ruled carried-or-fixed | [glossary](../glossary.md#terminal-ledger); § 4.2 |
| governing plan | the campaign document a unit runs under: its scope, its **guardrails** (owner-set constraints no agent may waive), and its dated **Change Log** of accepted designs. For the current campaign this is the compiler rebuild's systems-conversion plan | the campaign's own repository |
| parity gate | pre-wiring check: the new path reproduces the old path's observable behavior on the unit's test battery | § 4.5 |
| landed gate | post-deletion check: the plan's predicates re-verified after the old path is removed | § 4.5 |

```text
        ┌──────────────────────────────────────────────────────────┐
        │                        (next unit)                       │
        v                                                          │
  [1 INVENTORY] ──> [2 DESIGN] ──> [3 REVIEW] ──> [4 OWNER GATE] ──> [5 BUILD]
   finder            designer       warden /        owner              │
        ^               ^  ^        advocate          │                │
        │               │  │           │              │                │
        │               │  └─ FAIL ────┘              │                │
        │               └──────────── RETURN ─────────┤                │
        │                                             │                │
        │   (inventory defect found at 2 or 3)        │ REJECT         │
        └─────────────────────────────────────────────┼── (terminal:   │
                                                      │    recorded)   │
                        [2 DESIGN] <── design defect at a gate ────────┘
```

Transitions, named: Step-3 **FAIL** → Step 2. Step-4 **RETURN** → Step 2.
Step-4 **REJECT** → terminal (the rejection and its reasons are recorded
in the governing plan; the unit ends). A failure at any step whose root
cause is an **inventory defect** → Step 1. A Step-5 **gate failure** →
the implementer if the defect is in the implementation, or Step 2 (via a
fresh Step-3 review) if the defect is in the design. Step-5 **landed-gate
pass** → the unit is committed and the pipeline repeats for the next unit.

### 4.1 Step 1 — INVENTORY

- **Actor:** source-machine-finder. **Input:** a source scope and an
  intake brief (P-D).
- **Deliverable:** the Machine Inventory (§ 5 adds the architecture map to
  this deliverable when it ships).
- **Obligations:** static analysis only; every claim carries file:line;
  every machine entry carries its full terminal/error set (latent ones
  included) and a disposition in the RFC-0059 P1 vocabulary.
- **Exit criterion:** the inventory exists. It is the **entry gate** for
  design (RFC-0059 P3): no conversion work enters Step 2 without one.

### 4.2 Step 2 — DESIGN

- **Actor:** frame-fsm-designer. **Input:** the Step-1 inventory.
- **Deliverable:** the design record — the target system architecture, its
  composition with existing systems, and a verification plan (the factored
  reference implementation, the differential test against it, and the
  regeneration check).
- **Obligations:**
  1. **Verify upstream.** The designer MUST spot-check every inventory
     claim its design depends on against the source. Claims verification
     is every stage's duty, not only the reviewer's. A discovered
     inventory defect returns the unit to Step 1.
  2. **Disposition vocabulary.** Every ruling is *reify* (payoff named) or
     *leave latent* (plea and void condition named) — never "not a
     machine" (RFC-0059 P1).
  3. **The terminal ledger.** The record MUST enumerate every terminal and
     refusal state of the code being replaced — including
     [glossed](../glossary.md#glossing) ones: merged errors, silent
     clamps, swallowed failures — and rule each one **carried** (with
     justification) or **fixed** (with the new named state). A terminal
     MUST NOT be dropped silently. This is the state-faithfulness
     guarantee: a differential test cannot provide it, because the hand
     code being replaced is the differential's own reference
     implementation, and its glosses ride across unexamined.
- **Exit criterion:** the record is complete, ledger included.

### 4.3 Step 3 — INDEPENDENT REVIEW

- **Actor:** a reviewer who did not produce the design — the **delivery
  warden** (§ 3) for contract fit against the governing plan, the advocate
  for machine honesty, or both. The designer never certifies its own work.
- **Input:** the design record, its input inventory, the governing plan,
  and the source.
- **Obligations:** re-verify the design's load-bearing claims by the
  reviewer's own reading; attack the terminal ledger adversarially (hunt
  for terminals it missed — a missed terminal is a failing finding); check
  contract fit, precedent conformance, and scope discipline; flag anything
  that belongs to the owner's authority (guardrails, scope) rather than
  the design's.
- **Deliverable:** a verdict — **PASS**, **PASS-WITH-CONDITIONS** (the
  conditions listed), or **FAIL** (the defects listed) — with findings
  ordered by severity.
- **Exit transitions:** PASS and PASS-WITH-CONDITIONS proceed to Step 4
  (conditions attached); FAIL returns the work to Step 2 (or Step 1, if
  the root cause is an inventory defect).

### 4.4 Step 4 — OWNER GATE

- **Actor:** the human owner. Guardrail and scope decisions are made here
  and only here; no agent waives either.
- **Input:** the reviewed design and the reviewer's conditions.
- **Deliverable:** a ruling, recorded as a dated entry in the governing
  plan's Change Log.
- **Rulings (exit transitions):** **ACCEPT** — the design becomes a
  recorded change and a scheduled unit of work (→ Step 5); **ACCEPT with
  conditions** — the conditions become part of the recorded change
  (→ Step 5); **RETURN** — back to Step 2 with direction; **REJECT** —
  terminal; the rejection and its reasons are recorded.

### 4.5 Step 5 — BUILD

- **Actors:** the implementer (working inline in the main session, or a
  narrowly-scoped builder agent), the test author (writes AND runs the
  batteries), and the delivery warden, which runs both gates.
- **Input:** the accepted design record and its conditions.
- **Deliverable:** the implemented unit — source, generated artifacts,
  tests, and the deletion of the replaced hand path — landed as one
  recorded change.
- **Obligations and gates:** the **parity gate** runs before the new path
  is wired into production (the new path MUST reproduce the old path's
  observable behavior on the unit's battery); the **landed gate** runs
  after the old path is deleted (the plan's predicates re-verified). On a
  gate failure: an implementation defect returns to the implementer; a
  design defect returns the unit to Step 2 via a fresh Step-3 review.
- **Exit criterion:** the landed gate passes; the change is committed.
  The pipeline repeats for the next unit.

### 4.6 Why the layers — evidence from the first traversal

The first end-to-end traversal (logged in § 10; a scanner-conversion unit
of the compiler rebuild) demonstrated the design rationale empirically:
**every stage caught a defect the previous stage missed.** The inventory
missed one latent terminal — a body/no-body fork decided by a byte search
that ignores string-literal boundaries, so a brace inside a string
literal flips the fork. The designer's terminal-ledger pass caught it.
The designer's ledger in turn missed one terminal — a silent clamp whose
edge case constructs an invalid span and panics debug builds. The
reviewer's adversarial ledger hunt caught it. The reviewer then surfaced
one exception to an owner-set guardrail and one overclaim in the
governing plan's own ledger — both matters only the owner may rule on,
routed to Step 4. No single stage was defect-free; the layered pipeline
converged. Verification is layered because every stage is fallible in a
way the *next* stage's obligations are specifically shaped to catch.

## 5. Local analysis — the architecture map *(exploratory)*

The local tier: one scanned scope, in-memory relations, single-process
reasoning. A Machine Inventory lists machines; the **architecture map**
organizes them so a designer can reassemble that scope's architecture
from the analysis alone.

- **The spine — drive traces.** For each **entry event type** a process
  accepts (public calls, handled messages, endpoints, `main`), the
  single-threaded chain of activity traced end to end: every machine hit,
  in activation order, until the chain returns or reaches an asynchrony
  seam. The drive hierarchy is the overlay of these per-event traces.
  Multiple hierarchies (one per root that no other machine drives) are
  expected; a single-machine hierarchy is information, not noise — it
  tells the designer that machine composes at the pipeline level or not
  at all.
- **Relations are facts; packaging and transport are annotations.** Two
  machines related in-memory, across packages, or over a wire are equally
  related — the edge is typed and annotated with how it is carried. The
  four edge types: ***drives*** — A's activity invokes B's transitions
  synchronously; ***feeds*** — A's output is B's input without A invoking
  B; ***refines*** — B is a finer quotient of A's state (one state of A,
  opened up, is B); ***shares-leaf*** — A and B both drive the same
  sub-machine, which is recorded once and marked shared (sharing is
  single-source structure made visible). A local map records the *near
  end* of every wire relation; the relation completes locally if the far
  end is in scope, else at global port joining (§ 6).
- **The seam register.** Every **asynchrony seam** — thread spawn,
  channel or queue post, callback registration, wire call — ends one
  drive chain and starts another, and always hosts a protocol machine
  (retry, timeout, correlation, session, backpressure). The map records
  each seam, its transport, its protocol machine, and the chains it
  separates. A seam whose far end is outside the scanned scope is
  recorded as an unresolved **port** for the global tier to join.
- **Interfaces.** Every machine entry carries what it consumes and what
  it yields — the composition contract without which the map shows *that*
  machines connect but not whether they can.
- **Overlays.** Packaging within the scope (module/crate placement,
  cross-package drive edges) ships with the map. Threading signals (spawn
  sites, channel endpoints, entry-thread context) are collected as
  annotations when the source makes them cheap to gather; they never gate
  the map's delivery.
- **Descriptive, never prescriptive.** The map records the latent
  architecture as it exists. Which axis becomes system composition, which
  becomes hierarchy within a system, and which stays a leaf is the
  *designer's* decision, made downstream.

## 6. Global analysis *(exploratory — advanced tier, builds on local)*

The global tier relates systems across the boundaries a single local scan
cannot cross. Every global capability consumes completed local maps —
their machines, seam registers, and unresolved ports — and joins them;
none re-derives what local analysis already produced.

- **Boundary preprocessing — the rough cut (probably the first step).** A
  global preprocessor that carves the codebase estate — every repository
  and deployment unit in scope — into its natural, language-specific
  system-hosting boundaries: workspaces, crates, packages, modules,
  services, build and deployment units — *before* any deep scan. Its
  output is the partition that scopes the local engagements (one local
  map per carved boundary, or a stated grouping) and the skeleton the
  later joins hang on. It is the global engagement's init state: cheap,
  breadth-first, and structural — it names where systems live, not what
  they are. Deferred until the local tier's contained-environment test —
  the directory-scale benchmark of § 10: § 5's map produced for one
  self-contained module and graded against a known answer key — is
  complete.
- **Port joining.** Matching the unresolved ports of separate local
  maps — the wire call in one process to the route/topic/queue handler in
  another, across repositories where necessary — turning recorded seam
  *ends* into cross-process relations. The joined pair plus the protocol
  machine at the seam is one composed system, whatever the transport;
  relatedness is invariant under packaging and carriage.
- **Component and packaging organization.** How the discovered systems
  are distributed across components, packages, and deployment units —
  including the cases where related machines are packaged together and
  the cases where one system's halves live in different units.
- **Concurrency structure.** Organizing local threading annotations into
  a process-level picture: which machines run on which threads or tasks,
  where drive chains hop, and the channel/queue protocol machines at each
  hop. Secondary by declared priority, desirable where the signals
  permit.
- **Global drive.** The end-to-end extension of the local spine: an entry
  event traced through its local chain, across a joined seam, into the
  next process's chain — the distributed analogue of § 5's per-event
  trace.

Global analysis is explicitly out of scope for a single finder
engagement; it is a separate engagement (and likely a separate agent in
the family) whose inputs are local maps.

## 7. Scaling the pipeline *(exploratory)*

Three connected designs for running the pipeline wider than one unit at a
time. Each is design-in-motion; the two-lane trial below is the agreed
next experiment.

### 7.1 The per-system design fleet

Step 2 parallelizes as a fleet of **temporary, per-system design agents**
— one per system in the unit's scope, each tuned to exactly that system's
requirements and the interactions it will have (its neighborhood in the
map). A fleet agent designs; it does not build or run. Its ancillary
duties are **unit-test construction** — authored, not executed: the same
mind that rules on each terminal-ledger entry writes the test that
exercises it (carry rulings get pinning tests, fix rulings get directed
tests), making the ledger executable — and **documentation** (the
system's module header, its spec in prose). Authored-but-unrun tests are
marked as such; Step 5's test author runs them and takes ownership.

Authority is split in two levels. **Macro-architecture** — which systems
exist, the hierarchy, the interfaces *between* systems — stays with one
mind (the designer role of § 3, informed by the map). **Micro-design** —
a system's internal states, its side of each interface, its ledger, its
tests, its docs — belongs to that system's fleet agent. This split is
what prevents locally-elegant designs that do not cohere: coherence was
never the fleet's job.

Collaboration is staged and structured, not conversational: leaf-owning
agents design first and publish their interfaces (as structured interface
lines, not prose); dependents design against published interfaces; a
dependent needing more files a structured change proposal to the owner;
irreconcilables escalate to the macro-architect, guardrail matters to the
owner. All of it happens inside Step 2 — interface negotiation at design
time is design; after the owner gate it would be drift.

**Agreed next experiment:** a two-lane trial — two per-system design
agents in parallel, each delivering design record + terminal ledger +
authored battery + module documentation, reviewed and gated as a batch.

### 7.2 The system graph — one data structure

The architect's output boils down to a single **system graph**: a highly
annotated DAG that holds everything the builder needs. It is the same
species of object as the architecture map (§ 5) — which is the point:
the finder emits the **as-is** graph, the architect emits the **to-be**
graph, the builder implements the **diff**, and the delivery warden diffs
the as-built result against to-be mechanically.

- **Nodes** are machines: kind (system / leaf / driver / reference
  implementation), **status** (`exists` / `new` / `modify` / `delete` /
  `demote-to-reference`), interface, registers, file target, precedent
  pointer, documentation text — and, fractally, the node's interior as a
  Frame source skeleton, since the notation for a machine's inside
  already exists.
- **Edges** are the § 5 types plus two the design phase adds:
  **replaces** (to-be node → as-is node) and **verified-against** (the
  differential obligation, attached to the edge between a new node and
  its reference implementation).
- **The terminal ledger becomes graph annotation**: each terminal of a
  replaced node points at the to-be state that names it (carried) or the
  directed test that pins its change (fixed).
- **Build order is derived**, not written: topological layers of the
  diff, with phase tags where a unit lands in stages.
- **Decisions vs. arguments.** The graph holds every *decision*; a linked
  prose appendix per node holds the *argument* (alternatives, evidence).
  The builder consumes the graph alone; reviewers and the owner get graph
  plus appendix.
- **Sharing.** Agents share the graph by reference — path plus stable
  node IDs, never copies. It shards one-file-per-node with a hub-owned
  edge file, so write ownership is structural (P-C): a fleet agent can
  write only its own node's files. Version control is the transaction
  log; as-is, to-be, and as-built are versions of one structure. Fleet
  briefs are then **subgraph extraction**: an agent's tuned context is
  mechanically its node plus one-hop neighborhood.

- **Explain — derived reports, never authored ones.** An `explain`
  operation projects the graph into prose, parameterized by **scope**
  (whole graph, the diff, one node, one drive trace) and **audience**
  (the owner gate reads the diff narrated — what is new, modified, or
  deleted, terminals carried vs. fixed, exceptions, build order; the
  reviewer reads claims, evidence, and the full ledger table; the
  builder reads ordered per-node work orders; documentation readers get
  the architecture as narrated walkthroughs). The default renderer is
  deterministic code, so the report says exactly what the graph says;
  a model-narrated layer, if added, composes over the deterministic
  render — never over the raw graph — and cites node IDs for every
  claim. Because rendering walks the whole structure, explain doubles
  as the graph's linter: a missing interface, an unruled ledger entry,
  or an orphan port surfaces exactly where the prose goes blank. Prose
  design records thereby become *outputs* of the graph rather than
  siblings kept in sync with it.

The schema is grown empirically, not invented: the two-lane trial's
agents emit the graph as a deliverable alongside their prose records,
the first accepted design record is transcoded into it as the
calibration pilot, and the explain renderer is validated by
regenerating reports we already trust from hand-written practice and
comparing.

The first trial delivered the schema's first consolidated amendments —
both lanes, firewalled from each other, independently discovered the
same gaps: edge type **`routes-through`** (a leaf that runs another
system — the codebase's most characteristic composition, which
`drives`/`shares-leaf` misdescribe); ledger ruling
**`carry-and-name`** (behavior byte-exact, but the terminal gains a
named register — the most common ruling in practice, invisible to a
carry/fix binary); a top-level **`[[deltas]]`** array (recorded
behavior changes as governing-plan Change Log hooks); plus structured
register entries, leaf sign-off surfaces, decision points with
alternatives and break inputs, interface preconditions, and node-level
runtime constraints. Lifecycle is a status field, never a
self-referencing edge.

### 7.3 Hosting — a supervised runtime for the tree of agents

The orchestration currently lives in an interactive session. Its target
home is a supervised runtime: **Heron**, a sibling project — a controller
architecture of Frame state machines over a message bus, running a
supervised sense→decide→act loop under a coordinator, with a DAG walk
that has dependency propagation, branch-halt failure poisoning, durable
per-node state files, and an event log. The fit is direct:

- **The tree of agents lives in the decide layer** as deterministic Frame
  machines — the pipeline machine plus one agent-manager machine per
  engagement — while **the model engagements are effectors**: the
  nondeterministic act at the boundary, invoked from a task envelope
  (intake brief + extracted subgraph), returning a result envelope plus
  artifacts. Nondeterminism confined to act; orchestration deterministic
  and auditable.
- **The operational stall protocol reifies** into the agent-manager
  machine's states (launching, running under a patience budget, suspect,
  killed, single retry, narrowed fallback) — supervised by the
  coordinator instead of by vigilance.
- **The graph's shard layout coincides** with the runtime's per-node
  durable state files; the fleet's failure semantics coincide with
  branch-halt poisoning (a failed lane skips its dependents, siblings
  survive); the owner gate models as a control envelope the pipeline
  waits on.

Sequencing: the two-lane trial runs in-session; hosting waits until the
system-graph schema stabilizes, because the graph is the mission's plan
format. The main build to get there is the agent effector host.

## 8. Shared protocols

- **Intake** (P-D): shipped and behaviorally validated — an agent handed
  a scope with no purpose, deliverable, or depth responded with a
  grounded proposed intake brief and did no unscoped work.
- **Operational discipline** (handling slow or silent agents) is process,
  not architecture, and lives in the project's process documentation. Two
  architectural consequences are recorded here: when a result gates the
  next step, agents SHOULD run synchronously (a synchronous run surfaces
  errors directly and cannot be misjudged from the outside); and any
  signal used to judge whether a background agent is alive MUST first be
  calibrated against an agent known to be healthy — this family once lost
  three healthy agents to an uncalibrated signal.
- **Independence.** Parallel reviewers of one target MUST NOT read each
  other's in-progress work; benchmark runs MUST be firewalled from prior
  reviews and design records of the same target.

## 9. Alternatives considered

- **One omnibus advisor carrying all roles.** Rejected on measurement:
  the added roles paid for themselves in *findings* only in the document
  and audit domains, while roughly tripling engagement cost and blurring
  the advisory role's short, conversational cadence. Domain focus
  preserves both.
- **A single agent for advising and finding (RFC-0059 § 9's ruling) —
  reversed here.** RFC-0059 rejected a separate machine-finder agent on
  fork-risk grounds: two documents carrying one worldview would drift.
  P-A resolves that objection — both agents load the *same* canonical
  paper, and instruction files are packaging, not worldview — and the
  P-B measurements justify the split by domain. This RFC supersedes that
  ruling; RFC-0059 carries the corresponding supersession note.
- **Worldview duplicated per instruction file, no canonical text.**
  Rejected — RFC-0059's experiment showed the paper alone carries the
  capability; duplication invites fork and drift (P5).
- **Dynamic verification inside the scanner.** Rejected: builds bought
  nothing for machine-finding, roughly tripled runtime, and its parallel
  test runs polluted each other's results; auditing is its own domain
  (P-B, P-E).
