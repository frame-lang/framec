# RFC-0060: Scan-time diagnostics for ambiguous and malformed native regions

- **Status:** Draft
- **Author:** Mark Truluck <mark.truluck@cogiton.com>
- **Created:** 2026-07-21
- **New terms:** [fork-and-adjudicate](../glossary.md#fork-and-adjudicate), [scan-time diagnostic](../glossary.md#scan-time-diagnostic)
- **Builds on:** RFC-0056 (framec as a real compiler), RFC-0056.1 (the most restrictive machine), RFC-0057 (the rebuilt compiler), RFC-0039 (parser as composed Frame machines)

The key words **MUST**, **MUST NOT**, **SHOULD**, **SHOULD NOT**, **RECOMMENDED**,
and **MAY** are to be interpreted as in RFC 2119.

## Summary

framec **delimits** native code; it does not parse it. Almost every ambiguity of a
host language therefore never reaches framec — the native text is opaque to
*interpretation*, and only its *boundaries* are scanned. Two boundary-affecting
situations are the exception: **lexical forms** (strings, comments, chars,
lifetimes, heredocs, interpolation — the regions that decide where code ends and
data begins) and the **generics-vs-comparison `<>` split** inside a Frame
parameter or argument list (`Map<K, V>` versus `x < y, z > w`).

This RFC establishes one property and one contract. The property: **detection is a
strictly weaker, decidable, semantic-free capability than resolution.** framec can
always *detect* that it is in an ambiguous or malformed situation during the scan —
even the C++-style `<>` case it cannot *resolve* without a type system — and it
detects it **by construction**, because a [fork-and-adjudicate](../glossary.md#fork-and-adjudicate)
scanner carries both readings in one pass and their divergence *is* the ambiguity.
The contract: framec **SHOULD** surface those detections as [scan-time
diagnostics](../glossary.md#scan-time-diagnostic). The flagship is a new **warning,
`W417`**, for an ambiguous `<`/`>` in a declaration-site parameter default — the
one place framec today silently guesses. This RFC specifies that warning precisely,
generalizes the diagnostic channel, and draws the line between the residual that
diagnostics answer (the *undecidable* `<>` fork and *malformed* input) and the
residual that **resolution** answers (the decidable lexical forms), with the
parser capability matrix as the standing guard between them.

## Motivation

### framec does not parse native code — so most ambiguities never arrive

Under the [Oceans Model](../glossary.md#oceans-model), framec transforms only Frame
constructs; native type strings and native statement bodies pass through verbatim.
A consequence that is easy to miss: framec is not exposed to the host language's
grammar. A `?:` here, an overloaded operator there, a macro, a template
metaprogram — none of it is framec's problem, because framec never asks what the
native text *means*. It asks only one question of native text: **where does it
end?** That question has to be answered to find the closing brace of a handler
body, the top-level commas that separate Frame's parameters, the `)` that closes an
instantiation. Answering it requires knowing which bytes are *code* and which are
*string/comment/char content* (so a `,` or `}` inside a literal does not miscount),
and how *delimiters nest*.

So the situations that can actually confuse framec are exactly the ones that affect
**boundaries**:

1. **Lexical forms.** A scanner that miscounts a brace because it did not recognize
   a Ruby heredoc, a Rust raw string, a Lua long string, or a `'a` lifetime will
   mis-delimit the region — accepting the wrong extent, or rejecting legal code.
   These are the bugs catalogued in the rebuild's parser work (a family tracked as
   the char/lifetime opacity carry, and a batch of confirmed splitter bugs).
2. **The `<>` split.** Inside a Frame parameter or argument list, a top-level `<…>`
   is genuinely ambiguous: it may be a generic/template (`Map<K, V>` — the inner
   comma is *not* a separator) or a pair of comparison operators (`x < y, z > w` —
   the commas *are* separators). This is the C++ `f(a<b, c>d)`
   context-sensitivity: resolving it in general requires name and type lookup that
   a type-ignorant translator does not have.

Nothing else about native code makes framec guess. This narrow surface is what
makes the problem tractable — and what makes a complete diagnostic set feasible.

### Detection is decidable and semantic-free even where resolution is not

The `<>` case looks, at first, like it forces framec into one of two bad choices:
guess a reading, or refuse to scan the region at all. Both are wrong, and both are
the failure modes of state-machine authorship in disguise (*Shadows* §6.4): to
guess is to *gloss* a fork into a single arm; to bail out is to decline to build a
machine that is plainly there.

The resolution is that **detecting the ambiguity is a different, weaker problem
than resolving it.** To *resolve* `a<b, c>d` you must know whether `a` is a generic
type — a semantic fact. To *detect* that the region is ambiguous, you need only
observe that **two syntactic readings both survive the scan**: reading the angles
as brackets yields one segmentation, reading them as operators yields another, and
here they differ while neither is contradicted by the bytes. That observation is
decidable, requires no type system, and is *semantic-free*. It is strictly weaker
than resolution — it never says *which* reading is right — but it is exactly what a
diagnostic needs.

### Detection is a property of the correct-class machine, not a bolt-on

The rebuild's argument-list scanner already computes this. It is a two-counter
automaton that carries **both** angle hypotheses in a single left-to-right pass:

- a merged bracket-nesting counter (the segmentation under *angles-as-operators*),
  and
- a second angle-nesting counter, valid only under *angles-as-brackets*, together
  with a viability bit that is cleared the moment the bytes contradict the bracket
  reading (a `>` with no open `<`, or an unclosed `<` at the end).

At each top-level comma the walk records whether that boundary also holds under the
bracket reading. When the two segmentations coincide, there is nothing to
adjudicate. When the bracket reading stays viable *and* its boundaries diverge from
the operator reading's, the scanner has **detected a genuine fork** — and it did so
*by construction*, as a side effect of scanning at the right computational class,
not by a separate ambiguity-checking pass bolted on afterward. The scanner reports
the relationship as one of three outcomes — the hypotheses coincide; only the
operator reading is viable; or both are viable and diverged — and defers the
*choice* to a party that can make it.

This is the [fork-and-adjudicate](../glossary.md#fork-and-adjudicate) factoring of
*Shadows* §6.4, and it generalizes past the angle case. A **recognition machine**
that recognizes a lexical form by target detects an unterminated or unrecognized
form the same way — by recognizing (or failing to recognize) it. So the claim
"framec can detect every situation it must diagnose" reduces to a claim already
tracked elsewhere: **every scanner runs at the computational class its construct
demands.** The parser capability matrix (a standing test in the rebuild that pairs
each scanner's *capability* against its construct's *demand* on two axes — opacity
and nesting — and fails when any scanner is deployed below its class) is precisely
the guard that keeps detection complete. "Detect every situation" is the same
statement as "the capability matrix is all-green."

### The one place framec silently guesses today

The argument list — the **call site**, `@@Name(...)` — already adjudicates. When
its scanner reports a fork, the fork rides the tree, and the validation pass holds
each candidate reading against the system's **declared arity**: if exactly one
reading fits the declaration, it is chosen; if neither fits, or both fit, that is
an error (the call-site arity diagnostic, provisionally `E407` in the rebuild). The
call site can do this because a call has a downstream oracle — the declared
parameters — and adjudication is just holding the fork against it.

The **declaration site** — the `@@system Name(...)` header, and the state/handler
parameter lists — has **no such oracle.** A declaration *is* the arity; there is
nothing downstream to check it against. So the declaration-site scanner, faced with
a viable fork, applies a fixed policy: **favor the template** (read the angles as a
generic). This is correct for the overwhelmingly common case — every generic type —
and it is faithful to the legacy behavior. But for a balanced comparison-operator
straddle across adjacent defaults it is knowingly wrong, and today it is wrong
*silently*:

```frame
@@system Foo(a: int = x < y, b: int = z > w) {
    interface:
        step()
    machine:
        $Idle { step() {} }
}
```

The `<` of `a`'s default and the `>` of `b`'s default balance across the comma, so
favor-the-template merges the two parameters into one — `a`, with a malformed
default `x < y, b: int = z > w` — and **drops `b` entirely.** framec then emits a
constructor with a single parameter. The mistake is bounded (it is rare, and the
malformed native text it emits is rejected loudly by the target compiler rather
than corrupting data silently), but the *guess itself* is invisible: nothing tells
the author framec chose a reading, or that another reading existed. That silence is
the wrong way to make a decision framec cannot make correctly.

## The contract

This RFC specifies scan-time diagnostics in three parts: the flagship declaration-
site warning (`W417`), the general diagnostic channel that carries any scanner's
detection to the user, and the division of labor between diagnosis and resolution.

### 1. Flagship — `W417`, ambiguous angle in a declaration-site parameter default

**Name:** `ambiguous-param-angle`. **Severity:** Warning. **Family:** W4xx
(semantic warnings), the declaration-site sibling of the call-site arity error.

#### Detection (normative core)

The declaration-site parameter scanner **MUST** surface its angle-fork outcome on
the tree, as data, in the same shape the call site already uses: *no fork*, *only
the operator reading viable*, or *both readings viable and divergent*. This is the
detection guarantee, and it **MUST** be unconditional and semantic-free — it is a
property of the fork, computed during the scan, and framec **MUST NOT** consult any
type information to produce it.

Surfacing the fork on the tree changes **no emission**: framec's resolution policy
remains **favor-the-template**, unchanged from today. `W417` is *additive
visibility* over a decision framec already makes — never a change to which code is
generated.

#### The declaration-site adjudicator (the warning trigger)

The call site adjudicates a fork against declared arity. The declaration site has
no arity, but it has a weaker, semantic-free oracle available for free: **is each
candidate reading a well-formed parameter list?** — that is, does every segment
parse as `name [: type] [= default]` with `name` a bare identifier. framec already
computes an identifier check for this exact purpose elsewhere in the same scanner
family; reusing it requires no type parsing.

The diagnostic **SHOULD** be emitted when, and only when, **both** readings of a
detected fork are well-formed parameter lists:

- If exactly **one** reading is a well-formed parameter list, framec **MUST** take
  it and **MUST NOT** warn. This silences the common generic case: for
  `store: Map<K, V>` the operator reading splits into `store: Map<K` and `V>`, and
  `V>` is not a valid parameter (its name is not an identifier), so only the
  template reading is well-formed and it is chosen in silence — exactly today's
  behavior, now *justified* rather than merely defaulted.
- If **both** readings are well-formed parameter lists, the site is genuinely
  undecidable without types (`a: int = x < y, b: int = z > w` reads as one
  malformed-default parameter *or* as two clean comparison-default parameters, and
  the bytes do not choose). framec **MUST** apply favor-the-template as before and
  **SHOULD** emit `W417`.
- If **neither** reading is well-formed, the input is malformed; see §2 (the
  refusal channel), not `W417`.

This trigger mirrors the call-site error exactly — *both-admissible is diagnosed,
never guessed* — with parameter well-formedness standing in for declared arity as
the declaration-site oracle. It is the concrete realization of unifying the split
sites on one disambiguation rule.

**Emission-invariance lemma (favor-the-template is provably preserved).** The
"exactly one well-formed → take it" clause can never select the operator reading
over the template reading, because **O-well-formed implies G-well-formed**: each
merged template segment takes its name from its run-initial operator segment, so
the template reading's names are a subset of the operator reading's names — if all
operator names are identifiers, so are all template names. The adjudicator
therefore decides only *whether to warn*, never *which code to emit*; on a
both-viable fork framec always emits the template reading, exactly as today, and
`W417` is pure added visibility.

> **Residual (honest scope).** Parameter well-formedness silences ordinary generics
> but not *any viable generic fork with a top-level comma whose trailing angle
> segment itself reads as a parameter head* — an identifier followed by `:` or `=`.
> The class includes associated-type bindings (`HashMap<K, Item = V>`, whose
> operator reading `HashMap<K` / `Item = V>` is all-identifier-named) and
> inline-defaulted type parameters (`Foo<A, B = X>`). For every member of this
> class both readings are well-formed parameter lists, so `W417` fires even though
> favor-the-template is correct. Because `W417` is a **warning** and the favored
> reading is right (the emission-invariance lemma above guarantees it), this is
> bounded noise, not a wrong program; the author parenthesizes or ignores it.
> Eliminating it needs a finer, still type-ignorant signal (operator spacing /
> adjacency), which is deferred resolution work, not detection — see Alternatives.

#### Message and suggested fix

The diagnostic **MUST** carry the offending list's span, name both readings, state
that framec read the angles as a generic (the favored policy), and point at the
zero-syntax fix — parenthesization:

```
W417: ambiguous `<`/`>` in a parameter default of `@@system Foo(...)`
      read as a generic (framec favors the template when it cannot tell):
        as generic brackets (1 param): `a: int = x < y, b: int = z > w`
        as comparison operators (2 params): `a: int = x < y` · `b: int = z > w`
      framec cannot resolve this without a type system, so it guessed.
      help: parenthesize the comparison to disambiguate — `a: int = (x < y)`
```

The parenthesization fix is **structural, not advisory**: framec counts angles only
at bracket-nesting depth 0, so a `<` or `>` inside `(...)` sits at depth ≥ 1 and is
never counted under either hypothesis. Wrapping *either* straddling operand in
parentheses removes its angle from the question, collapses the fork, and lets the
comma split cleanly. This is verified behavior: `a: int = (x < y), b: int = z > w`
emits the intended two-parameter constructor.

### 2. The general diagnostic channel for scanners

`W417` is one instance of a general pattern: **any fork-and-adjudicate scanner MAY
surface its divergence, and any recognizer MAY surface an unterminated or
unrecognized form, as a scan-time diagnostic.** This RFC defines how such a
diagnostic reaches the user, because framec's scanners cannot mint diagnostics
directly.

**The constraint.** The boundary scanners are pure and total: they read bytes and
produce spans (and, in the fork case, a viability record), and a malformed input
degrades to a named *refusal* (unterminated opaque region, stray closer, unclosed
group) rather than a panic. They live in the text layer, which by construction
holds no symbol table and no span-bearing diagnostic type — diagnostics with spans
are minted by the tree-walking validation pass, which has no bytes. Neither half
can raise a user diagnostic alone.

**The channel (normative).** A scan-time diagnostic **MUST** reach the user by
*riding the tree*, in two steps:

1. The scanner **records the condition as data on the node it produces** — the fork
   outcome on an instantiation node or a system-parameter node, a refusal reason on
   the node whose region refused. This is a fact framec put there about framec's own
   scan; it is not a fact about the user's native text, so recording it respects the
   Oceans Model.
2. The validation pass **reads that node and mints the diagnostic with a span.**
   This is exactly how the call-site arity error already works, and how `W417`
   works: one shared adjudicator over the recorded fork, consumed by validation for
   the diagnostic and by emission for the candidate choice.

**Concretely, at the declaration site.** The fork **MUST** be recorded via a new
`ParamAngles` value mirroring the call site's `ArgAngles` — `Inert` / `Operators` /
`Forked { alt }` — on the system-parameter node, where `alt` carries the *operator*
reading as **structured parameters** (not bytes), so validation checks identifier
shape over tree data exactly as the call site checks arity. The change is confined
to the parameter-scanner **wrapper**: it stops collapsing the fork to one reading
(it already computes both — the template/merged fold and the operator fold both
exist) and maps the outcome onto the tree the same way the call-site wrapper
already does. The parameter-scanning **machine is unchanged** — it already stamps
the viability and per-boundary bits the fork needs, so there is **no `.frs` edit, no
regeneration, and no bootstrap fixpoint**. The diagnostic's **span** is the
parameter-list / header span, which the header node already carries.

**Today's gap.** The call-site *fork* already rides the tree and is adjudicated. The
call-site *refusal* channel (unterminated opaque, stray closer, unclosed group,
dropped empty segment) is currently computed but **dropped at the production seam**
— it is observability only, not yet a user diagnostic. The declaration-site *fork*
is likewise collapsed inside the scanner today and not recorded on the tree. This
RFC's channel closes both: the fork **MUST** be recorded at the declaration site
(for `W417`), and the refusal channel **SHOULD** graduate from observability to
user diagnostics through the same tree-riding path. The natural home for the
refusal diagnostics is the deferred closed-world validation layer (spec §1167),
which already owns the general system-name and arity checks; until it lands, the
refusal channel remains recorded-but-unsurfaced, and that is a stated deferral, not
an oversight.

Scanners **MUST NOT** be given a direct diagnostic-emitting capability. Keeping the
scanners pure — facts out, diagnostics minted downstream where spans and the symbol
table live — is what keeps a single question (a fork, a refusal) from being
answered two different ways by two different passes, the defect class this
architecture exists to prevent.

### 3. Diagnose the undecidable; resolve the decidable

A diagnostic is the right answer for a situation framec **cannot decide**. It is the
*wrong* answer for one it can. The two boundary-affecting families divide cleanly:

- **The `<>` fork is undecidable** without a type system, so its residual — the
  both-admissible declaration-site case, and the both-admissible/neither-admissible
  call-site case — is answered by **diagnosis** (`W417` and the call-site arity
  error). Malformed input (a reading that is well-formed under neither hypothesis,
  an unterminated literal) is likewise answered by diagnosis via the refusal
  channel.
- **The lexical forms are decidable.** Whether a `}` sits inside a Ruby heredoc, a
  Rust raw string, a `'a` lifetime, or code is a *recognition* question with a
  definite answer once the scanner knows the target's forms. The correct response
  is therefore not to warn but to **resolve** — teach the recognizer the form, or
  make the opacity target-aware. A scanner that warns "I might be inside a heredoc"
  when it could simply recognize the heredoc has misdiagnosed a class deficiency as
  an ambiguity. For example, the declaration-site scanner's use of `"`-only opacity
  (rather than target-aware opacity) mis-scans a `'…'` char default or a Rust
  lifetime; the fix is a target-aware char-vs-lifetime recognizer, **not** a
  warning.

The parser capability matrix is the standing guard for this division: a cell where a
scanner's capability is below its construct's demand is a **resolution** task (route
through the higher-class machine); the genuinely ambiguous `<>` delimiter is the
*only* construct the matrix marks as additionally needing an adjudicator, and it is
the only one whose residual is a **diagnostic**. Diagnostics **MUST NOT** be used to
paper over a scanner deployed below its class; that is a bug to fix, not a condition
to report.

### Invariants preserved

- **Type-ignorance (Oceans Model).** Every diagnostic in this RFC is produced
  without framec understanding any user type. Detection reads byte structure — angle
  balance, identifier shape, delimiter nesting, opacity — and never the *meaning* of
  a type. `W417`'s adjudicator is an identifier check, not a type check. framec
  still emits the user's type strings verbatim; a diagnostic observes the boundary,
  it does not interpret the interior.
- **Backend-agnostic.** These diagnostics fire at the scan, before any target
  backend runs, on Frame's own delimiters. `W417` is target-independent (the
  declaration-site scanner is target-free); the lexical-form *resolution* it defers
  to is where per-target reality lives, and that is correctly the recognizer's
  concern, not the diagnostic's.
- **Detection completeness ⇔ scanners at class.** The guarantee "framec detects
  every situation it must diagnose" is not an independent obligation to audit; it is
  discharged by the capability matrix staying all-green. A new below-class splitter
  is a detection gap *and* a matrix failure, caught the day it is written.

## Examples

**Benign generic — one parameter, no warning.** The operator reading (`store: Map<K`
/ `V>`) is not a well-formed parameter list, so the template reading is taken in
silence:

```frame
@@system Cache(store: Map<K, V>) {
    interface:
        step()
    machine:
        $Idle { step() {} }
}
```

**Ambiguous straddle — `W417`.** Both readings are well-formed parameter lists;
framec favors the template (one parameter, `b` merged away) and warns:

```frame
@@system Foo(a: int = x < y, b: int = z > w) {
    interface:
        step()
    machine:
        $Idle { step() {} }
}
```

**The fix — parenthesize, no new syntax.** A `<`/`>` inside `(...)` is never
angle-counted, so the fork collapses and the comma splits into two parameters:

```frame
@@system Foo(a: int = (x < y), b: int = z > w) {
    interface:
        step()
    machine:
        $Idle { step() {} }
}
```

(These blocks are illustrative — they name undeclared identifiers to exhibit the
boundary construct. The three behaviors above were confirmed against the rebuild's
scanner: `Map<K, V>` yields one constructor parameter, the straddle yields one and
drops `b`, and the parenthesized form yields two.)

## Alternatives

**A dedicated escape syntax `@@(...)`.** An early idea was a Frame-level marker that
tells the scanner "the text inside is an operator expression, not a generic," e.g.
`a: int = @@(x < y)`. **Rejected as unnecessary surface.** Ordinary parenthesization
already disambiguates with zero new syntax: framec counts angles only at
bracket-depth 0, so `(x < y)` removes the angles from *both* hypotheses'
consideration. Adding `@@(...)` would introduce a Frame construct whose only job is
to do what `(` `)` already do, and would have to be taught to every backend as a
strip-on-emit token. The parenthesization fix is what `W417`'s help text
recommends.

**Keep favor-the-template, but silent (the status quo).** framec already favors the
template; the question is only whether to *say so* on a genuine fork. **Rejected.**
A decision framec cannot make correctly, made silently, is precisely the design
this project treats as a defect — the burden of proof is on leaving a fork
un-surfaced, and no plea holds here: the fork is real, both readings are viable, and
the author is the only party who can resolve it. `W417` is the honest form of the
same policy.

**Make it an error, not a warning.** Reject the ambiguous straddle outright.
**Rejected.** Favor-the-template still *emits* a reading, and where that reading is
right (every ordinary generic, and even the associated-type residual) an error would
reject correct programs. The mis-merge's downstream native text is rejected loudly
by the target compiler when it *is* wrong, so a warning is the calibrated severity:
it makes the guess visible without blocking the common case. The call site, which
*can* prove neither reading fits, does raise an error — because there it has the
arity oracle to prove wrongness. The declaration site cannot prove wrongness, only
ambiguity, so it warns.

**Warn on every detected fork.** Emit the warning whenever the angle hypotheses
diverge, without the well-formedness adjudicator. **Rejected as noise.** Every
generic type carrying a top-level comma (`Map<K, V>`, `Result<T, E>`,
`HashMap<K, V>`) produces a genuine fork — the scanner cannot distinguish it from a
comparison straddle without more signal. Warning on all of them would fire on
routine, correct code. The parameter-well-formedness adjudicator is the minimum
type-ignorant discriminator that silences those cases while still catching the real
straddle, which is why it is the specified trigger rather than the raw fork.

**Type-hint extraction to resolve the fork.** A best-effort, still type-ignorant
heuristic — a known-generic registry, or operator-spacing/adjacency (`Map<K` tight
against an identifier reads as generic; a space-surrounded `<` reads as operator) —
could *resolve* more straddles and even suppress the associated-type residual.
**Deferred, not rejected.** This is *resolution*, strictly stronger than the
*detection* this RFC delivers, and it must not regress the common generic cases. It
is future work layered on top of `W417`; the warning is the honest floor that holds
regardless of how far resolution later advances.

## Migration

Source-additive. `W417` is a new warning; it changes no generated code, because
framec's favor-the-template resolution policy is unchanged — the warning only makes
an existing decision visible. Programs that today compile with a silent mis-merge
will now compile *and* emit `W417`, pointing at the parenthesization fix; programs
that never triggered the fork are unaffected. The refusal-channel diagnostics
described in §2 are gated on the deferred closed-world validation layer and
introduce no behavior change until that layer lands.
