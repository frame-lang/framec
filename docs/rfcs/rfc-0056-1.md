# RFC-0056.1 — The Descent

- **Status**: Draft
- **Author**: Mark Truluck
- **Amends**: [RFC-0056](rfc-0056.md) (foundations). This RFC adds no principles; it defines the
  **method and the evidence** by which RFC-0056's machine principles (P2, P3) are carried out.
- **Companion**: the Machine Family RFC (`@@efsm` and the certified strata).
- **Scope**: A validation battery, and a disciplined descent from the most powerful construct to the
  weakest one that provably suffices — machine by machine, gated by tests.

---

## 1. Summary

For every machine in framec, find the **most restrictive language class that still solves the
problem**, and *prove* it by construction: implement it in that class and show the battery still
passes.

The method is a **descent**. Start where the problem demonstrably works. Demote it one class at a
time. Each demotion is accepted only if a construct-agnostic test battery — correctness *and* cost —
remains green. When a demotion fails, the machine has found its floor, and that floor is a **fact**,
not an opinion.

---

## 2. Motivation

### 2.1 Nobody ever proved the floor, so everything drifted upward

framec's machines were written in whatever construct was to hand, and then justified afterwards.
The results are on record:

- The **shipped `@@fsm` is Turing-complete** — a two-counter Minsky embedding compiles clean — while
  its own spec claims "regular-language only."
- `ExprScannerFsm`'s doc-comment and its tracking issue **both call it a PDA**. It is a counter
  automaton; the code counts *any* opener and *any* closer and never matches kinds.
- A proposed `@@pda` was argued (by this author) to be *required* for framec's bracket scanners. It
  is not: `push$`/`pop$` already does kind-matched, string-aware nesting to depth 20,000. **framec
  needs a stack nowhere** — every one of its six nesting scanners is a counter automaton.

Three claims about machine power, three wrong, all in one codebase. **Power was asserted, never
measured.** The descent exists so that it is measured.

### 2.2 The weakest class is not pedantry — it is what buys the certificate

RFC-0056 P3: the keyword is a machine-checked certificate. But the *value* of the certificate scales
inversely with the power of the class:

| Class | What you get |
|---|---|
| regular (`@@fsm`) | O(n) time, O(1) memory, guaranteed termination, **decidable equivalence & inclusion**, canonical minimal form, full Boolean closure |
| counter / pushdown | O(n) time, memory bounded by depth; equivalence decidable only in restricted subclasses |
| register | decidable equivalence under determinism + equality-only guards |
| `@@efsm` | structure and types checked; **no language-theoretic claims at all** |

Every step *down* the lattice buys a stronger guarantee. Sitting at `@@efsm` when a problem is
regular means paying nothing and getting nothing — and, worse, it means the machine *could* be
changed into a Turing tarpit by a one-line edit that no checker would notice.

### 2.3 And a machine at the wrong level is how the costumes happened

RFC-0056 §2 records the causal chain: `@@system` could not borrow its input → scanning was O(n²) →
so the scan logic was hand-rolled into native loops → so the mode landed in a native local → **which
is the string-blindness bug family**. Authors were forced to choose between a real machine and an
acceptable cost, and they rationally chose cost.

**The descent therefore cannot be a correctness exercise alone. If the weakest class that is
*correct* is unaffordable, authors will defect again.** So cost is measured — thoroughly, and in the
open — even though it never disqualifies a machine. **In production the most efficient approach wins
by default; the battery exists so that choice is made from data instead of from folklore.**

## 3. The method

The key words **MUST**, **MUST NOT**, **SHOULD**, **MAY** are per RFC 2119.

### D1 — The battery is the invariant, and it is construct-agnostic

The battery **MUST** test the **task**, not the implementation. A task is a specification — inputs to
expected outputs — and *any* candidate implementation, in any construct, is judged against the same
specification.

The battery **MUST** be written **before** any machine is ported. A machine ported first and tested
after has no invariant; it merely has a new implementation and a hope.

### D2 — The descent, and its acceptance rule

For each machine:

1. Establish it in a construct where it demonstrably works (its **incumbent**).
2. Attempt the next class **down**.
3. **Accept the demotion if and only if the battery's CORRECTNESS axis stays green** (cost is
   recorded, never a veto — D4).
4. Repeat until a demotion fails. That is the machine's **floor**, and it **MUST** be recorded, with
   the failing evidence, as a reviewed claim.

A demotion that "mostly works" is a **failed** demotion. A demotion that requires changing what the
machine *accepts* is not a demotion at all — it is a different machine (see D5).

### D3 — The lattice is not a chain

The strata do **not** form a line. **Stacks and registers are incomparable:**

- a pushdown machine recognizes `aⁿbⁿ`; a register machine cannot;
- a register machine recognizes `{w c x c w}` (a heredoc's `<<<ID … ID`); a stack **cannot** — a
  stack reverses, and you would need a queue.

So the descent finds the **minimal element(s)** of the lattice for a given problem, and there **MAY**
be more than one incomparable minimum. The classifier (D6) **MUST** report all classes a machine
qualifies for, not "the" class.

*(This corrects the sequencing in the original plan, which treated `@@efsm → @@pda → @@fsm` as a
chain. `@@rfsm` sits beside `@@pda`, not below it.)*

### D4 — Cost is MEASURED, never a disqualifier

**There is no cost qualifier.** This is a validation and data-gathering instrument, not a gate.
**Production always uses the most efficient approach by default** — so a machine is never *rejected*
for being slow; the data simply informs which implementation ships.

Only **correctness** gates. A candidate that disagrees with the task specification, or that changes
the language it accepts (D5), fails. Everything else is **recorded**.

The battery **MUST** measure and report, per task and per candidate:

1. **Asymptotic class.** Time at *n*, *2n*, *4n*, *8n*. Report the growth ratio: ~2× is linear, ~4×
   is quadratic. *(This is the measurement that would have exposed the 71-copy skipper years ago — it
   degraded 4× per doubling and nothing in the repository said so.)*
2. **Copying.** Bytes copied per probe. A positioned probe should be 0; if it is not, **say so and
   say why** (`@@system` cannot borrow — #209).
3. **Constant factor**, relative to the fastest candidate for that task.

The point of measuring cost is not to fail machines. It is that **cost pressure is what produced the
costumes**: authors faced a real choice between a correct machine and an affordable one, chose
affordability, and put the mode in a native local — which *is* the string-blindness bug family. The
numbers exist so that trade is made with evidence, in the open, once — instead of silently, by each
author, forever.

### D5 — A demotion MUST NOT change the language recognized

This is the trap the whole exercise exists to avoid, and it is already demonstrated:

> Bounding a nesting scanner's depth at K makes it regular — and **changes what it accepts**. At K=3,
> `(a(b(c(d)e)f)g)` closes one bracket early, the region ends at 13 instead of 15, `accepted == true`,
> **no diagnostic**, and the tail leaks into the next region. The *sound* variant (trap instead of
> saturate) does not mis-scan; it **rejects legal user source** at depth K+1.

Both are wrong. **A certificate obtained by changing the accepted language is not a certificate; it
is a silent miscompile with a badge.** Any demotion that narrows or widens the accepted language
**MUST** be rejected, and the boundedness — not the arithmetic — **MUST** be named as the reason.

### D6 — The classifier is the mechanism, not a human

The descent **MUST** be driven by `framec classify` (Machine Family RFC §8), which reports, for any
machine, the strongest stratum whose strips it satisfies and, for each stronger stratum, the exact
first violation. Hand-classification is how framec acquired three wrong power claims. **A rule that
can only be checked by reading is not enforced.**

## 4. The battery

### 4.1 The task corpus

Every scanning/recognition job framec actually has. Each task is specified independently of any
construct:

| Task | Known class (to be *verified*, not assumed) |
|---|---|
| skip line comment / block comment / hash comment | regular |
| skip string (with escapes) / triple string / template literal | regular (+ counter for `${…}` nesting) |
| Rust raw string `r###"…"###` | counter (match *n* hashes) |
| find line end | regular |
| balanced expression scan (`expr_scanner`) | **counter** — *not* a PDA |
| balanced paren end / top-level arg split | counter |
| Ruby `%q(...)` with nested delimiters | counter (closer fixed by a register at open) |
| PHP heredoc `<<<ID … ID` | **register** — not context-free |
| **native statement delimitation, brace targets** | counter (block depth) |
| **native statement delimitation, Python/GDScript** | **pushdown** — an indent-level **stack**; a dedent must pop to a *matching* prior level, so the levels must be remembered, not counted |
| body closer (per language) | counter + lexical modes |

Note the last two: they are **new** — required by RFC-0056 P1/P4 (the body AST needs a per-target
delimiter). They are the only place in framec where a **stack** is genuinely required, and they are
therefore the real customer for `push$`/`pop$`.

### 4.2 The correctness axis

1. **Differential.** Every candidate implementation of a task, plus the incumbent native
   implementation, **MUST** agree on every input. Disagreement is the finding.
2. **Adversarial.** The fuzz corpus **MUST** include the shape that produced every bug in this family:
   **a hostile-but-legal string or comment in an ordinary place.** A delimiter inside a string; a
   Frame construct inside a comment; a terminator inside a trailing comment.
3. **Positioned.** Each probe **MUST** be driven at *every* cursor position over one buffer and agree
   with the incumbent at every comparable position — not merely at position 0.

### 4.3 The cost axis

Per D4. Note the expected first result, so it is not mistaken for a regression:

> **`@@system` is expected to measure as quadratic today.** Its domain field must own its input, so a
> positioned probe copies the buffer on every call — 71 such sites, ~4× per doubling. That is not a
> failure of the battery; it is the battery **doing its job**, and it is the baseline against which
> P9 (universal borrowed/positioned input) is judged. **Measure it red first, then fix it, and let
> the numbers show the fix.**

### 4.4 The report — the battery's actual deliverable

The battery **MUST** be instrumented and **MUST** emit a report. The report — not a pass/fail line —
is the artifact that answers this RFC's question: *for each problem, what is the weakest machine that
solves it, and what does it cost?*

**Correctness gates. Cost is reported.** Wall-clock constants are not portable across machines; they
are still exactly what we want to read. So the report records everything and the harness fails only
on a correctness or language-change verdict.

**Measurement discipline** (so the numbers mean something):
- fixed, committed input corpus, so runs are comparable;
- warm-up iterations discarded; **median** of N repetitions reported, with the spread;
- report the machine and compiler version alongside the numbers — a constant without a substrate is
  a rumour.

**Required content**, per *task* × *construct* × *input size*:

| Field | Meaning |
|---|---|
| `ns_per_element` | median, with spread |
| `growth_ratio` | time(2n)/time(n) — **the gated quantity** |
| `asymptotic` | `linear` \| `quadratic` \| `other` — derived from `growth_ratio`, **gated** |
| `bytes_copied` | per probe. **MUST be 0** for a positioned probe — **gated** |
| `allocations` | must not grow with input length |
| `relative_cost` | × the fastest candidate for this task |
| `correctness` | `agrees` \| `DISAGREES` (differential + adversarial) |
| `verdict` | `PASS` \| `FAIL(correctness)` \| `FAIL(language-changed)` — **never** `FAIL(cost)` |

Emitted in two forms from **one** source (a second emitter drifts — framec already carries three
divergent literal emitters): **JSON** for the ratchet, and a **human table** for reading.

**And the report MUST show the descent itself** — that is the whole point. Per task: every construct
attempted, its verdict, and the resulting **floor** with the evidence for why the next demotion
failed. Shape:

```
TASK: balanced expression scan (expr_scanner)
  incumbent   native Rust loop     1.1 ns/el   1.00x   linear   copies=0    agrees   PASS
  @@efsm      + depth domain var   1.4 ns/el   1.27x   linear   copies=0    agrees   PASS
  @@fsm       + int(0..64)         1.2 ns/el   1.09x   linear   copies=0    DISAGREES
                                   ^ FAIL(language-changed): at depth 65 the region closes one
                                     bracket early. Not a demotion — a different machine. (D5)
  @@system    push$/pop$          92.0 ns/el  83.6x    linear   copies=n    agrees   PASS
                                   ^ CORRECT, but 84x and copies its input (#209). Recorded, not
                                     rejected — production picks the fastest correct candidate.
  FLOOR: @@efsm + counter (a one-counter automaton).
         Not @@fsm: unbounded nesting is not regular, and bounding it changes the language.
         Not @@pda: it never matches delimiter kinds — a stack buys nothing here.
```

That table *is* the answer. A `FLOOR` line is a **reviewed claim**: it records the compiler version
and the failing evidence, and it **MUST** be re-derived (D6, §6.3) after any language change — a floor
asserted once and trusted forever is how framec acquired three wrong power claims.

## 5. The programme

**S0 — the battery.** Task corpus, differential harness, adversarial fuzz axis, cost harness with
asserted asymptotics. Incumbents (today's native implementations) are the reference. Expected: the
`@@system` candidates are **red on cost**.

**S1 — `@@system` parity.** Make `@@system` a first-class machine host:
- **P9 / #209** — the input-source abstraction (an *indexed accessor*, not a borrow concept), so a
  machine can scan input it does not own. Universal across targets.
- **#211** — `push$ -> $State(args)` currently **drops the args** (runtime `IndexError`; all 17
  backends). The `StackPush` node carries only a target *name* while its sibling `Transition` carries
  the args — *a node that cannot hold what the parser found.* This is not a curiosity: it is the exact
  mechanism the Python/GDScript indent-stack delimiter needs, so it is **on the critical path for the
  body AST**.
- **Progress / termination** — a scanner that spins **hangs framec on a user's source file**.

  **Gate:** the battery passes for `@@system` on both axes. *If the cost axis still fails on the
  constant factor — see §6.1 — that is a finding that changes the plan, not a detail to wave through.*

**S2 — `@@fsm` → `@@efsm`.** The rename, plus the family features (Machine Family RFC): the honest
certificate, `over`/`scan_at` universal, progress default-on, and the reservation of `stack` / `push`
/ `pop` as keywords. *(Today they are **not** reserved: `push(1)` silently parses as a bare expression
and emits `self.return_value = self.push(1);`.)*

**S3 — descend to `@@efsm`.** Port each `@@system` machine that can be. Re-run the battery. The
descent is only real if the battery is the judge.

**S4 — descend further.** For each machine, use the classifier to attempt the minimal class(es):
`@@pda` where a stack is genuinely required; `@@rfsm` where a register is; **`@@fsm` wherever
regular suffices** — which the census suggests is *most* of them. Record each floor with its
evidence.

**Expected shape of the result** (a prediction, to be falsified): most skippers land at `@@fsm`; the
counter family lands at `@@fsm`+counter (a certified *one-counter* automaton, which is strictly weaker
than a PDA and separately certifiable); heredoc lands at `@@rfsm`; and **only the Python/GDScript
statement delimiter needs a stack.** If that holds, `@@pda` has exactly one customer — which is worth
knowing *before* building it.

## 6. Risks and honest limits

### 6.1 The constant-factor risk — the most likely way this goes wrong

`@@system` dispatch goes kernel → router → state handler, and RFC-0020's model allocates an
`Rc<FrameEvent>` (plus a context push/pop) **per event**. A scanner that feeds one event per input
byte therefore allocates **per byte** — still O(n), but with a constant factor perhaps 50–100× a
compiled DFA table. (A `push$`/`pop$` bracket scanner measured ~90 ns/byte; a DFA is ~1 ns/byte.)

**If that is confirmed, `@@system` is the right *pushdown* machine and the wrong *scanner host* for
hot paths**, and recognizers belong in `@@efsm`/`@@fsm` — which is where the descent was heading
anyway. **But we take that conclusion from the measurement, not from the argument**, and the machine
is not disqualified: it is *recorded*, and production picks the fastest correct implementation.

### 6.2 A green battery is not a proof of equivalence

Differential testing shows *no observed disagreement*, not equivalence. The one place framec can do
better is `@@fsm`: Hopcroft minimization gives a canonical form, so **two certified `@@fsm`s are
provably equivalent iff their `language_hash` matches**. Where both candidates are certified regular,
the battery **SHOULD** assert hash equality and not merely behavioural agreement. *(This is also the
tool that would have caught framec's two divergent recognizers of its own grammar — 21 `@@` forms
vs. 6 — which currently diverge silently.)*

### 6.3 The floor may be a moving target

A machine's floor depends on what the language can express. `expr_scanner`'s floor was reported as
"PDA, native by necessity" and was in fact `@@fsm`+counter all along — the claim was wrong *and* the
enabling feature (positioned input) had already shipped. **Record floors with their evidence and the
compiler version, and re-run the classifier after any language change.** A floor asserted once and
trusted forever is how we got here.

## 7. Unresolved

2. **Where does the battery live?** In-tree (`cargo test`, fast, no toolchains) or in
   `framec-test-env` (real toolchains, slow)? The cost axis needs stable timing; the correctness axis
   wants the 17-backend matrix. Probably both, split by axis.
3. **Certified one-counter automata.** If most of framec's scanners are counter machines, is a
   one-counter certificate worth minting as its own stratum (decidable equivalence, strictly weaker
   than pushdown), rather than forcing them up to `@@pda` or down to a *bounded* — and therefore
   **wrong** (D5) — `@@fsm`?
4. **`@@pda`'s visibly-pushdown strip is a hole** (validated): every real framec scanner is
   string-aware, so the same symbol is a *call* in code and *internal* inside a string — which is not
   visibly pushdown. The fix is to run the PDA over a **`token`** alphabet, layered on a certified
   `@@fsm` lexer, making it a two-machine story. This must be settled *before* `@@pda` is specified.

---

## 8. Delivery

The battery ships **first as a standalone local harness**, not wired into `cargo test` or CI.
Rationale: timing wants a quiet machine and a fixed corpus, and a flaky gate in CI is how a guard
becomes an `#[ignore]`. It is a **laboratory instrument** before it is a **ratchet**.

- Standalone runner; one command; emits the JSON + the human table (§4.4).
- The correctness axis is portable and **SHOULD** be imported into the 17-backend matrix once the
  task corpus is stable.
- The cost axis stays local until its numbers are reproducible enough to be worth gating on — if ever.
  Per D4 it never gates anyway; it *informs*.
