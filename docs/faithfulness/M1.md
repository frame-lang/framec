# M1 — Foundation (Kernel & Dispatch)

Milestone core for the faithfulness grid. Read by `faithfulness-builder` (the target behavior) and
`faithfulness-warden` (the DoD inventory). Language-neutral: the **behavior** is here; each target's
**spellings** are in `docs/faithfulness/lang-<t>.md`.

## What M1 lands

The runtime/kernel skeleton every system needs before any feature. A system with no HSM, no actions,
no push/pop, no persist must be **byte-identical to legacy** after M1. Concretely, the emitted
program for a system contains:

- **Runtime types** (fixed, system-name-substituted → native leaf): a FrameEvent, a FrameContext
  carrying a **return slot** (`_return`) + a data map, a Compartment carrying `state`, `state_args`,
  `state_vars`, `enter_args`, `exit_args`, `forward_event`, `parent_compartment` (+ a `copy`).
- **The kernel** (fixed → native leaf): the constructor/`_create` factory, `__prepareEnter` /
  `__prepareExit`, and `__kernel` with the **transition-drain loop** (route, then drain queued
  transitions: exit the leaf, switch compartment, synthesize `$>`/forward, mark contexts
  transitioned), and `__transition`. These are constant across all systems (verified: two
  structurally different systems emit a byte-identical engine block, only the router arms differ) —
  so they are **emitted fixed text**, never reified.
- **`__router`** (varies with the state list → **RouterWalk `@@system`**): dispatch to `_state_X`.
- **Interface wrappers** (per interface method → EmitInterface `@@system`): build the event, push a
  context, run the kernel, **read the return slot** and return it.
- **State dispatchers** `_state_X` (states × handled events → StateDispatchWalk `@@system`).
- **Handler methods** `_s_X_hdl_...` (per handler → EmitHandlers `@@system`).
- **Construction seeding** of domain fields (→ DomainInitWalk `@@system`) and the `_HSM_CHAIN`
  (→ HsmChainWalk `@@system`; for a flat system every chain is the singleton).
- **Statement lowering** (StmtWalk `@@system` + leaves): a Frame assignment, a transition `-> $B`
  (→ prepareEnter + `__transition` + terminate), and a value return `@@:(e)` (→ write the return
  slot; see the behavior note below).
- **Lifecycle**: `$>`/`<$` are driven by the kernel drain, not spelled as direct calls; handler
  param binding pulls from `state_args` / event params / `enter_args` / `exit_args`.

## Universal behaviors M1 reproduces (these live in the SHARED layer, not a leaf)

- **Handler key-order**: dispatch arms and handler methods emit in handler-KEY order — exit before
  enter (arcanum key `$<` < `$>`), then user events alphabetically. Interface methods stay in
  declaration order. (`Backend::orders_handlers_by_key`, default true.)
- **Close-brace newline**: the `\n` immediately after a system's closing `}` belongs to the system;
  extra newlines / non-newline whitespace after `}` are water. (`consumes_close_brace_newline`,
  default true.)

## Structural variation points (the language pack specifies these)

M1's behavior is neutral, but its *realization* varies — the language pack must pin each:

- **Event representation** — a typed enum of variants (static targets) vs a string message (dynamic).
- **Return-slot typing** — how `_return` is typed in a statically-typed target (per-method? an
  `Option`? a union). Dynamic targets park a value; static targets must type it.
- **Compartment `state`** — a language enum vs a string.
- **`@@:(e)` termination** — whether the value-return spelling is terminal. It emits a real `return`
  on targets where the handler cannot continue past it (a `;`-return), and a NON-terminal slot
  *assignment* on targets where the handler runs on (Python). (`return_call_terminates`, per-language
  — the language pack states this target's answer.) Getting this wrong silently DROPS user code.

## Definition of Done — the M1 fixture inventory

Foundation is exercised by nearly every fixture, so M1's anchors are **minimal, foundation-only**
programs (no HSM `=> $^`, no actions, no push/pop, no persist). Each is a self-validating TAP
program (build the emitted code, run it, assert observable behavior) added to test-env so it is
durable and reused across languages. The cell is done when **every fixture below is byte-identical
to a freshly regenerated legacy oracle** for the cell's target (+ the universal gates F2–F6).

| Fixture (test-env `positive/foundation/`) | Foundation construct it pins | Source |
|---|---|---|
| `foundation_minimal` | 1 state, 1 interface method, `self.x = 1`, a domain field | author |
| `foundation_value_return` | `f(): int { @@:(5) }` — the return slot | author |
| `foundation_transition` | 2 states, `-> $B` flat transition + drain | author |
| `foundation_lifecycle` | `$>()` enter handler fired by the kernel drain | author |
| `foundation_enter_args` | `-> (99) $B` → `$>(a: int)` enter-arg delivery | author |
| `foundation_selfcall` | `x = @@:self.g()  @@:(x)` reentrant dispatch + slot | author |
| `control_flow/transition_basic.fpy` | minimal existing flat-transition fixture | reuse |

*Rebase note (per the DoD ruling):* this inventory is the intended M1 delta and may grow as we
discover an uncovered foundation construct; add the fixture here and to test-env when it does. Any
fixture whose byte-divergence is a *legacy bug ng fixes* moves to `intentional_divergences.txt` with
a runtime validator, not into this table.
